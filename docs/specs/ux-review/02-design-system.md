# Visual foundations and component inventory

## What is there now

**Chart color system** (`src/lib/design/palette.ts`, `palette.css`, `palette-validator.ts`, `palette.test.ts`, `index.ts`). A rigorous, tested token set for _data_ color only: eight fixed-order categorical hues, a 13-step sequential blue ramp, a three-tier certainty ramp, a four-level status scale (`good/warning/serious/critical`), and per-scheme surface/text/border tokens (`--surface-1`, `--surface-page`, `--text-primary/secondary/muted`, `--grid-line`, `--axis-line`, `--border-hairline`, `--delta-good`). Every hex is validated in both light and dark for OKLCH lightness band, chroma floor, CVD separation and contrast (`palette-validator.ts`), and `palette.test.ts` parses `palette.css` and asserts it matches `palette.ts` **exactly** (`toEqual`, not a subset check) for three literal blocks: `:root`, the `prefers-color-scheme: dark` media block, and `:root[data-theme='dark']`. Seen in `/tmp/shots/desktop-it/design.png` and `dark-it/design.png` — the only route that renders any of this today.

**Chart primitives** (`src/lib/design/charts/*.svelte`, exported from `index.ts`): `Axis`, `ChartFrame`, `DataTable`, `Grid`, `Legend`, `StatusIndicator`, `Tooltip`. These are well-built and mutually consistent — hairline axes, a mandatory table-view twin for every chart (`ChartFrame.svelte:17-21`), a status indicator that structurally cannot render color without an icon+label (`StatusIndicator.svelte:9,14-19`). `ChartFrame` also contains the one genuinely well-executed segmented control in the codebase: a two-button chart/table `view-toggle`, 6px radius, `overflow:hidden`, active state = filled `--text-primary` (`ChartFrame.svelte:59-66,104-127`).

**Layout primitives** (`src/lib/layout/{Card,Section,Page,RecordList}.svelte`). `Card.svelte` is a single `<div>` with a 1px hairline border and padding — no radius, no shadow, no elevation, no header slot, no variant (`Card.svelte:12-15`). `Section.svelte` is a heading + optional actions + 2rem top margin (`Section.svelte:24-46`) — the closest thing to a spacing-scale token that exists, and it's one hard-coded number. `Page.svelte` sets a 48rem/72rem content cap and delegates the header to `PageHeader.svelte` — out of scope here per the brief, but its `padding: 2rem` / `1rem` (mobile) values are two more spacing constants that don't reference anything. `RecordList.svelte` renders **two independent DOM trees** for the same data — a `<table>` (desktop) and a `<ul>` of definition-list cards (mobile), toggled by a CSS media query at 639px (`RecordList.svelte:28-30,81-148`) — the one deliberate, documented responsive-table pattern in the app; every _other_ table in the codebase (see below) has no such twin and either scrolls or overflows.

**`/design` route** (`src/routes/design/+page.svelte`). Renders the categorical palette, sequential ramp, status scale, a light/dark/system toggle, the validator report tables, and one illustrative chart. Its own subtitle says it outright: "this route renders the system for review — it is not a dashboard screen, and nothing on it is real data" (`+page.svelte:137`). It documents chart color. It documents **zero** interface concerns: no type scale, no spacing scale, no button, no input, no table chrome, no card, no badge inventory, no focus ring, no disabled state.

## What is wrong

1. **BLOCKER — there is no interface design system, only a chart design system, and the two are conflated in the one artifact that claims to document "the visual system."** `src/routes/design/+page.svelte` titles itself "Visual system" and is reachable from nowhere in the product nav, yet covers only chart color. Every interface decision — button, input, table, card, spacing, type — is invented per-file. For a product whose owner's complaint is "I don't like it at all," there is no single place to point at and say "make it look like this," and no artifact the other six workstreams can converge on. This is the root cause of every item below.

2. **BLOCKER — five different button/link visual languages coexist with no rule for which one to use where**, so the same action ("submit this form") looks different from screen to screen: a filled `--text-primary` CTA (`src/routes/+page.svelte:91-102`, "Registra una giornata" in `dashboard.png`), a bare `border px-4 py-2` outline button (used verbatim, with only spacing tweaked, across at least 17 forms — `ClientForm.svelte:161`, `ContractForm.svelte:284`, `RateCardForm.svelte:112`, `invoices/new/+page.svelte:268`, `mail/…/TemplateForm.svelte:125`, etc.), an underlined text link acting as a submit button (`+page.svelte:85` "Esci", `alerts/+page.svelte:23` "Impostazioni"), a Tailwind-utility filled button that is the _only_ place `rounded` + `bg-black`/`dark:bg-white` appears in the app (`offline/+page.svelte:12`), and the segmented "quantity preset" control on `/day/new` that reinvents `ChartFrame`'s toggle with 0px radius instead of 6px and a different disabled/selected treatment (`day/new/+page.svelte:220-232` vs `ChartFrame.svelte:104-127`). A one-person ledger that must be trusted needs one unambiguous visual grammar for "this is the action to take" — right now every screen re-derives its own.

3. **MAJOR — radius is six different numbers with no naming, so "how rounded is a corner" answers differently on every component**: `0` (`Card.svelte:13`), `4px`/`rounded` Tailwind default (`offline` button, `DayStateBadge.svelte:95`), `6px` (`Tooltip.svelte:41`, `ChartFrame` toggle, `/design` theme toggle `+page.svelte:374`), `8px` (`ChartFrame.svelte:84`, proposals card `proposals/+page.svelte:103`), `10px` (`CeilingMeter.svelte:109`), `999px` (nav alert badge `Sidebar.svelte:102`, proposals-count pill `+page.svelte:119`, meter track `CeilingMeter.svelte:139`). None of these values live in a variable; a future change means grepping six magic numbers across six files and guessing which are related.

4. **MAJOR — no typographic scale exists; font-size is 15+ ad hoc rem/px/clamp values with no named relationship**, in a product the brief calls "text-and-numbers dense." Observed sizes include `0.625rem` (`DayStateBadge` compact label), `0.6875rem`/`11px` (chart axis labels), `0.75rem` (badges, toggle labels), `0.8125rem` (tables, captions, secondary labels — used inconsistently as both a body-small _and_ a table-cell size), `0.875rem` (the single most common "body" size, but shared with buttons, form labels, and `RecordList`'s table font-size), `0.9375rem` (chart card titles), `1.0625rem`/`1.125rem` (two different, un-reconciled "h2" sizes: `+page.svelte:131` dashboard widget heading vs `Section.svelte:38` section heading), and `clamp(1.75rem, 6vw, 2.5rem)` for the one genuinely headline-sized number in the app (`CeilingMeter.svelte:124`). No modular scale, no line-height system, no weight scale beyond ad hoc `600`/`700`. `font-variant-numeric: tabular-nums` is applied correctly in four places (`RecordList`, `DataTable`, `Tooltip`, `CeilingMeter`) but that is a lucky convention, not a rule — nothing stops the next amount from being typed without it.

5. **MAJOR — "interface color" does not exist as a concept; every non-chart color decision borrows a chart token or a Tailwind default that has no interface meaning.** There is no `--color-primary`, no `--color-danger`/`--color-focus`, no surface hierarchy beyond `surface-1`/`surface-page` (two levels, not enough for a raised card _and_ a popover _and_ a selected row). Concretely: the "primary CTA" background is `var(--text-primary)` — text color repurposed as brand color (`+page.svelte:94-95`); form field error text is a raw Tailwind `text-red-700` never routed through the validated palette or checked for contrast in either scheme (`day/new/+page.svelte:112`, `day/[id]/+page.svelte:98`, and 6 more identical occurrences); the `worked_without_approval` badge — the single state the product needs unmistakable per its own promise "no day worked without approval goes unnoticed" — correctly uses the validated `--status-critical` token (`DayStateBadge.svelte:91-104`), while the proposals-pending pill next to it on the _same_ dashboard uses `--status-warning` for an unrelated meaning (count, not severity) with no token distinguishing "count badge" from "severity badge" (`+page.svelte:116-125` vs `DayStateBadge.svelte`). Chart status colors are validated against a 3:1 mark-contrast floor with an explicit "relief" carve-out (grayscale-safe via icon+label) — interface color has no floor, no carve-out, no test, at all.

6. **MAJOR — no focus, hover, disabled, or loading state exists for any interface control.** `grep` across every button and input in `src/routes` finds zero `:focus-visible`, zero `:hover`, zero `:disabled` style rules outside two `disabled={...}` _attribute_ bindings that carry no visual treatment (`settings/+page.svelte:68,78` — the push-notification buttons go inert with no dimming, no cursor change, nothing). Keyboard-only or switch-access use of a product whose own stated shortcut culture ("Premi N", "Ctrl+Invio") assumes keyboard fluency is currently unusable: there is no visible focus ring anywhere, native or custom. Submitting a form gives no loading affordance — a slow save on a 3G phone connection looks identical to a hang.

7. **MAJOR — error and validation presentation is inconsistent field-to-field and never associated with its input for assistive tech.** Every form repeats the same unlinked pattern: `{#if errors.x}<span class="text-xs font-semibold">{errors.x}</span>{/if}` (`ClauseNoteForm.svelte:32,39`, `ContractForm.svelte:92`, `RateCardForm.svelte:42`, `TemplateForm.svelte:44`, 8+ more) with no `aria-invalid`, no `aria-describedby` wiring the message to its field, and no consistent color (`text-xs font-semibold` in most forms, bare `text-red-700 text-sm` in `day/new` and `day/[id]`). A day ledger whose entire value proposition is "protect the consultant" cannot afford a validation message a screen reader user or a squinting-at-a-phone user can miss.

8. **MINOR — border/hairline usage is the one thing done consistently (`var(--border-hairline)`), but "hairline everywhere, nothing else" reads as unfinished** rather than deliberate austerity once you cross-reference it with the CTA, meter and tooltip, which _do_ use elevation-adjacent radius (6–10px) and solid fills — so the flat/hairline-only rule the lead identified in `Card.svelte` is already broken in three other first-party components, without being replaced by a coherent alternative.

9. **MINOR — density is undecided.** Table row padding is `0.5rem 0.75rem` (`RecordList.svelte:89`) vs `0.5rem 0.75rem` in `DataTable.svelte:54` (same, coincidentally) but form field padding ranges from `px-1 py-0.5` (`clients/…/[contractId]/+page.svelte:319`, an inline rebill select) to `px-3 py-3` (`day/new` and `day/[id]`, `text-base` sized for touch) to `px-4 py-2` (most submit buttons) to `px-4 py-3.5` (`proposals/[id]/+page.svelte:78,81`) — five distinct paddings with no rule for when a control is "compact" (inline, inside a table row) vs "comfortable" (a primary page action) vs "touch" (mobile-critical flows). `day/new`'s `text-base`/`py-3` sizing (`day/new/+page.svelte:110,122,181,197`) is the only place touch-target sizing was clearly intentional; it does not propagate to `day/[id]`'s approval-linking form on the same flow (`day/[id]/+page.svelte:89`, `border px-3 py-3` — matches by luck, not by shared component).

10. **MINOR — dark mode is an inversion of the interface, not a designed second scheme, everywhere outside the validated chart tokens.** `palette.ts`/`.css` correctly design light and dark independently (`palette.ts:13-16` — "designed as their own set rather than a mechanical inversion"). But the one hand-rolled dark-mode-aware rule in the whole route tree is `offline/+page.svelte:12`: `bg-black … dark:bg-white text-white dark:text-black`, a literal color inversion of exactly the kind the chart system's own comment disavows. Every other button/input in the routes never references `dark:` or a scheme-aware token at all — they inherit correctness only because they already route through `--text-primary`/`--surface-1`, which happens to flip correctly. That is luck, not policy; the day a hardcoded hex sneaks into a form (as it already has for validation red) dark mode breaks silently.

11. **POLISH — three separate, un-unified "badge/pill" implementations** with no shared component: the nav unread-count pill (`Sidebar.svelte:98-105`, hairline border, 999px radius, no fill), the dashboard proposals-count pill (`+page.svelte:116-125`, filled `--status-warning`, 999px radius), and `DayStateBadge`'s glyph+label pattern (`DayStateBadge.svelte`, no pill at all except the critical state's hatched box). A new "3 overdue" badge on `/invoices` (needed per finding #7 in the established list) has three existing precedents to copy from and no rule for which.

### Typographic scale

- **A. Adopt a numeric scale on the existing system-font stack.** Define 6–7 named steps (`--text-2xs` … `--text-3xl`) as `rem` values on a ~1.125–1.2 ratio anchored at a 16px body, map every existing ad hoc size in the inventory above onto the nearest step, keep the current unstyled system-UI stack (no new font, zero load cost). Effort S. Risk: low — pure substitution, `font-variant-numeric: tabular-nums` promoted from "used in four places" to a scale-level rule (`--text-tabular` mixin or a `.tabular` utility) applied to every money/count figure, not just the four that got it by luck. Does not fix: the app still looks like system-UI Arial/Segoe/San Francisco depending on OS, which reads as "unstyled" to a design-conscious owner regardless of how disciplined the scale is.
- **B. Scale + one self-hosted variable font for numerals and headings.** Same scale as A, plus a single self-hosted font (e.g. Inter or IBM Plex Sans — named and licensed, no CDN dependency, subset to Latin+Italian diacritics, `font-display: swap`) used for headings and the money/data-dense UI, with the system stack kept for body prose. Effort M (font subsetting, `@font-face`, FOUT handling, one extra static asset to version). Risk: medium — must verify Italian diacritics (à, è, ì, ò, ù) render correctly in the subset, and the 15%-longer Italian strings still fit headings at the largest scale step. Unlocks: a genuine typographic identity instead of "whatever the visitor's OS ships," and true tabular figures via the font's own `tnum` OpenType feature rather than CSS-only `font-variant-numeric` (which some system fonts partially ignore).
- **Recommendation**: B. This is a financial ledger the owner reads daily; a chosen, licensed, self-hosted typeface is one of the highest-leverage, lowest-risk ways to make it stop looking like a wireframe, and IBM Plex Sans/Mono ship genuine tabular lining figures the current system stack does only inconsistently.

### Spacing scale

- **A. Extract a token scale from what's already in use.** The values already in the codebase cluster near a 4px base (`0.125rem`…`0.375rem`…`0.5rem`…`0.75rem`…`1rem`…`1.5rem`…`2rem`) — name them `--space-1` (4px) through `--space-8` (32px) and swap every literal `rem`/`px` gap, padding and margin in `Card`, `Section`, `Page`, `RecordList`, and every route's inline `flex flex-col gap-1` etc. Effort S–M (mechanical but wide — every route file touches it). Risk: low. Does not fix: does not itself resolve the density question (#9) — a scale still needs a density policy layered on top (see below).
- **B. Scale + explicit density tiers.** As A, plus two named density presets (`comfortable`, `compact`) each mapping to a padding/row-height pair, so a table row, a form field, and a button consciously pick one rather than landing on whichever `px-N py-N` the author typed that day. `compact` for inline-in-table actions (the rebill select/button pair currently at `px-1 py-0.5`/`px-2 py-0.5`), `comfortable` for primary page actions and every touch-critical mobile control (matching `day/new`'s existing `text-base`/`py-3`, which becomes the _documented_ touch-target minimum rather than one page's accident). Effort M. Risk: low.
- **Recommendation**: B. The mobile-in-30-seconds promise depends on `day/new`'s touch sizing being the rule, not the exception; naming it turns a lucky outcome into an enforced one.

### Radius / elevation / border policy

- **A. Pick one radius scale, apply it by role, keep flat/hairline as the default.** Three named steps — `--radius-sm` (4px: badges, small chips), `--radius-md` (8px: cards, chart frames, dialogs), `--radius-full` (pills) — replacing the six unnamed values in evidence item #3. Card stays flat (no shadow), consistent with the lead's existing hairline-first read on it; `CeilingMeter`'s 10px and `Tooltip`'s 6px both round down to `--radius-md`. Effort S. Risk: low — visually near-invisible per-component, but removes the "why does this card have sharper corners than that one" tell.
- **B. Introduce a two-level elevation system (flat card + raised overlay) with radius attached to elevation, not chosen ad hoc.** Level 0 (page-embedded: `Card`, table rows) stays hairline/flat. Level 1 (overlays: `Tooltip`, a future dialog/toast/sheet) gets `--radius-md` + a single defined shadow token (`--shadow-overlay`, one soft shadow, not a stack of AI-slop glows). This gives the component set item 3 asks for (dialog, toast, tooltip) a real elevation language instead of each inventing its own `box-shadow` the way `Tooltip.svelte:42` currently does alone. Effort M. Risk: low-medium — must confirm a shadow reads correctly on both the light `#f9f9f7` and dark `#0d0d0d` page surfaces (test both).
- **Recommendation**: B. The component set explicitly needs dialog/toast/tooltip, all of which are overlays; defining "flat" vs "raised" once, rather than deciding it three separate times when those components get built, is the whole point of doing this centrally.

### Interface colour (surfaces, primary, semantic)

- **A. Add a thin semantic layer on top of the existing chart surface tokens, in a _separate_ CSS file/block.** New tokens — `--color-primary`, `--color-primary-ink` (text on primary), `--color-danger`, `--color-danger-ink`, `--color-focus`, plus two more surface steps (`--surface-2` for a nested/selected row, `--surface-overlay` for dialogs/tooltips) — validated for contrast the same way the chart palette is (reuse `contrast()`/`oklch()` from `palette-validator.ts`, which are already general-purpose color-math functions, not chart-specific). **Must** live in a new file (e.g. `src/lib/design/tokens.css`, imported after `palette.css` in `layout.css`) rather than inside `palette.css`'s `:root` block — `palette.test.ts:236-238` asserts `root.vars` via `toEqual` against an _exact_ expected object built from `palette.ts`; any additional custom property inside that same block fails the test immediately. Effort S–M. Risk: low if kept in its own file; high (breaks CI) if merged into `palette.css`.
- **B. Same as A, plus retire the "text-color-as-brand-color" pattern** (`var(--text-primary)` used as the CTA fill) by giving every filled/primary surface its own token pair from day one, so a future "make the primary action blue instead of black" decision touches one variable, not a search-and-replace across 17 forms. Effort M (touches every button in the inventory once the Button component lands — see below). Risk: low, sequenced after the Button component exists.
- **Recommendation**: B, executed together with the Button component build (next section) rather than as a standalone pass — token definition without a consumer just adds unused CSS.

### Buttons, links, and the "which control means submit" problem

- **A. Restyle in place: one `Button.svelte` with variants, mechanically swap all 35 `<button>` + submit-styled `<a>` call sites.** Variants: `primary` (filled, one per screen max), `secondary` (outlined hairline), `ghost`/`tertiary` (the current underline-as-button pattern, now legitimate and consistent instead of an escape hatch), `danger` (reject/delete-adjacent actions like `proposals/[id]`'s reject button, currently just `opacity-80` on the same border style as accept — `+page.svelte:81-84`). Each variant carries hover/focus/disabled/loading from day one (state item 6 above). Effort M (one component, ~35 call sites, mostly mechanical). Risk: low; the risk is scope creep into per-page copy/placement decisions, which is explicitly out of this area's scope — cap it at "swap the element, keep the label and position."
- **B. Restructure: collapse the five current visual languages down to three sanctioned ones and remove the rest.** Primary (filled) appears once per screen for the one recommended action; secondary (outlined) for everything else that is a real, self-contained action; tertiary/link (underline) _only_ for navigation, never for a destructive or state-changing submit — which reclassifies `+page.svelte:85` "Esci" (sign-out, a real state change styled as a link) and the reject-proposal button (a destructive action currently styled identically to accept, `+page.svelte:81-84`) as design bugs, not just inconsistency. Effort M, same component as A plus a short audit pass reclassifying ~6 misclassified call sites. Risk: low.
- **Recommendation**: B. The button component alone (A) fixes the paint; B fixes the one place button choice was actively hiding a distinction the product needs (destructive vs. safe, e.g. reject vs. accept a proposal) — cheap to do at the same time.

### Form controls: select, date, number/amount, text, textarea, checkbox/radio, file

- **A. Wrap natives, keep browser semantics.** `Select.svelte`, `DateInput.svelte`, `NumberInput.svelte`/`AmountInput.svelte`, `Textarea.svelte`, `Checkbox.svelte`/`Radio.svelte`, `FileInput.svelte` — thin wrappers around the native elements (native `<select>`/`<input type=date>` keep OS-level pickers, which matter on mobile — never replace `<input type=date>` with a JS date-picker library) that apply the shared border/radius/spacing/typography tokens and add the missing states (focus-visible ring, disabled, error). `AmountInput` specifically formats/parses through `$lib/money.ts`'s `MinorUnits` boundary so a form never round-trips a float through display state (today `ContractForm.svelte`, `RateCardForm.svelte` etc. all bind raw `value`/`bind:value` to un-typed strings). Effort M (7 small components + call-site swap across ~19 selects, 16 date inputs, 13 checkboxes). Risk: low; native semantics preserved, so no accessibility regression risk from reinventing `<select>`.
- **B. Wrap natives + introduce a `Field` wrapper that owns label/hint/error/required as a single contract**, so every one of the ~30+ `<label class="flex flex-col gap-1 text-sm">…{#if errors.x}<span>` blocks becomes `<Field label={..} error={errors.x} hint={..}>` with `aria-invalid`/`aria-describedby` wired automatically instead of re-typed per form (fixes evidence item #7 structurally, not just visually). Effort M, same components as A plus the wrapper. Risk: low.
- **Recommendation**: B — the error-association bug is a real a11y defect, not a style preference, and it costs almost nothing extra once the individual controls exist.

Effort M-L (one shared component, migrate 8+ call sites, each needs its card-row template defined). Risk: medium — migrating bespoke tables (e.g. the mail-template list with inline edit/send links) needs per-table review to preserve exact interactive elements in the card layout.

### Three visual directions

Each direction is described concretely enough to build a sample screen (e.g. the invoice list or the day-entry form) from the description alone. All three keep the validated chart palette untouched and reuse its status/certainty tokens; they differ in type, chrome, density, and how much visual weight is spent on the interface layer around the data.

**Direction 1 — "Ledger" (quiet, document-like, closest to current DNA).**
Type: system-UI stack kept (Option A above, not B) — this direction's whole point is that it doesn't need a new font because it leans into looking like a well-typeset financial document, not a "product." Two sizes do 90% of the work: 15px body/data, 13px secondary/meta, with a single 28px serif-free headline size reserved for the one figure per screen that matters (a ceiling, an invoice total). Color: near-monochrome — `--surface-page` a warm off-white (`#f9f9f7`, already in use), text in near-black, exactly one accent color (a deep blue reused from `--series-1`/`certainty-committed`) for links and the single primary action per screen; danger/warning reuse the existing status tokens verbatim. Density: compact, tight row heights (36px), generous only around the one primary CTA. Chrome: hairline borders everywhere (keep `Card.svelte` exactly as-is), zero shadows, radius capped at 4px. A table in this direction: dense rows, right-aligned tabular numerals, a hairline under each row, header row in the secondary text color with no background fill. A form in this direction: labels above fields, fields are a bottom-border-only "underline" input (no box) except selects/dates which keep a full hairline box for click affordance, one filled primary button bottom-right. This is the least risky evolution of what exists — it fixes every inconsistency in the inventory without changing the product's silhouette, which may or may not satisfy an owner who said "I don't like it at all" about that silhouette.

**Direction 2 — "Ledger, with confidence" (structured, banking-app-adjacent, most implementable of the three ambitious options).**
Type: self-hosted IBM Plex Sans for UI chrome + IBM Plex Mono for money/dates/reference numbers specifically (a deliberate typeface switch for numerals, not just a numeric feature flag — invoice numbers, amounts, and IDs render in mono, everything else in Plex Sans), a real 6-step scale (12/13/15/17/20/26px). Color: a genuine surface hierarchy — `--surface-page` light gray, `--surface-1` white cards with a _soft_ shadow (not a hairline) at 8px radius, one primary brand color independent of text color (a controlled blue, distinct from but harmonious with `--series-1`), semantic danger/warning colors that are UI-only siblings of (not reuses of) the chart status scale so a red button and a red chart mark are visually related but not literally the same token (avoids a future chart-token change silently reskinning every button). Density: comfortable, 44px row/control minimum everywhere (mobile-safe by construction), generous section spacing (32px between sections, per the existing `Section.svelte` margin, promoted to a token). Chrome: cards float slightly (shadow, not just border), badges are filled pills, primary buttons have real hover/active elevation change. A table here: card-wrapped, zebra-free (rely on row hairlines + hover highlight instead), a sticky header row with sort carets, sortable columns clearly indicated. A form here: fields have a full box with a 1px border that thickens/tints to the primary color on focus, inline validation appears below the field in the danger color with an icon, submit sits inside a sticky action bar on mobile (so "Salva" is always reachable without scrolling past the whole form — directly serves the 30-second promise). This is the direction most likely to read as "someone designed this" to a lay reviewer while staying implementable by one developer in Tailwind + a handful of components.

**Direction 3 — "Console" (dense, keyboard-first, data-terminal-adjacent).**
Type: IBM Plex Mono for _everything_, not just numerals — headings, labels, body, in a product that already has a documented keyboard-shortcut culture ("Premi N", "Ctrl+Invio") the current design buries as 9px gray afterthoughts; this direction promotes shortcuts to a first-class, always-visible affordance (a small `kbd`-styled tag next to the action it triggers, using a shared `KeyboardHint` component rather than a stray `<span class="text-xs opacity-60">`). Color: dark-first (dark is the default scheme, light is the override — inverse of today's implicit light-default), high-contrast, minimal chroma outside status/chart colors, which read as unusually vivid against the dark, near-black chrome by design. Density: very compact, 32px rows, tight leading, more information per screen (a return to something closer to the _current_ density, but disciplined). Chrome: no shadows, no radius beyond 2px, borders everywhere but _bright_ (higher-contrast hairlines than today's 10% alpha), status colors and the certainty ramp become the dominant visual interest against the muted chrome — closest in spirit to a well-typeset terminal dashboard. A table here: monospace, right-aligned numerals by default, minimal padding, sort/filter exposed as inline text controls rather than icon buttons. A form here: labels and inputs share one line where width allows (`label: [input]` rather than stacked), keyboard-first tab order visibly indicated, a persistent single-line command/shortcut bar. This direction is the biggest swing — it fully answers "I don't like it" with a distinct identity rather than a refinement, at the cost of being the least forgiving of Italian string-length overflow (mono characters are wider; the 15%-longer Italian strings need real headroom-testing at this density) and the most alien to a first-time desktop user expecting a conventional business app.

## Cross-cutting asks

The design system (tokens + component set) other areas should build against, not reinvent per-page:

- **Tokens file**: `src/lib/design/tokens.css` (new), imported in `layout.css` after `palette.css`, holding spacing (`--space-1`…`--space-8`), radius (`--radius-sm/md/full`), type scale (`--text-2xs`…`--text-3xl`, plus `--font-ui`/`--font-mono` once a direction is picked), semantic color (`--color-primary(-ink)`, `--color-danger(-ink)`, `--color-focus`, `--surface-2`, `--surface-overlay`), and `--shadow-overlay`. **Must not** add properties inside `palette.css`'s existing `:root`/dark blocks — `palette.test.ts:227-256` asserts those blocks' contents exactly.
- **`Button`** (`src/lib/design/Button.svelte` or `$lib/components`): variants `primary/secondary/tertiary/danger`; states default/hover/focus-visible/disabled/loading; `type="button"|"submit"`; used by every route currently doing `class="border px-… text-sm"` (17+ forms) or `class="… underline"` as a submit (6+ sites).
- **`Field`**: label + optional hint + optional error, wires `aria-invalid`/`aria-describedby`; wraps `Input`, `Select`, `DateInput`, `AmountInput`, `Textarea`, `Checkbox`, `Radio`, `FileInput`. Needed by every form in `clients/`, `day/`, `invoices/`, `mail/` (30+ label/error blocks today).
- **`AmountInput`/amount display helpers**: a display component (not just the existing `formatMinorUnits`/`formatAmount` functions in `$lib/i18n/format.ts`) that renders money at three defined sizes — headline (`CeilingMeter`-style, `clamp` + `--text-3xl` + bold), table-cell (end-aligned, tabular, `--text-sm`), inline-in-prose (tabular, weight 500, no size bump) — so InvoicesAndMoney and DashboardAndCeilings don't each invent their own amount treatment.
- **`Table`**: sortable, mandatory mobile-card twin (extending `RecordList`'s existing table/card duality), empty state, used by ClientsAndContracts, InvoicesAndMoney, IngestionAndMail (mail template list, register table) — flagged above as best sequenced _after_ those areas scope their per-page needs.
- **`Badge`**: `count` and `status`/`state` variants, consolidating `Sidebar`'s nav badge, the dashboard proposals pill, and `DayStateBadge`; needed by AlertsStatesAndPWA (alert counts) and DayLifecycle (state badges already built, should adopt the shared shell).
- **`Tabs`**: the `proposals/+page.svelte` status tabs (`In attesa`/`Accettate`/`Rifiutate`) are currently a hand-rolled `<nav>` of underlined links (`+page.svelte:38-49`); needed again wherever DashboardAndCeilings or InvoicesAndMoney add filtered views (e.g. "paid/unpaid/overdue" per finding #7).
- **`Dialog`/`Sheet`, `Toast`, `Banner`, `Skeleton`, `Tooltip` (interface, distinct from the chart `Tooltip.svelte`)**: none exist yet; every area will eventually need a confirmation dialog (destructive actions like proposal-reject, invoice void) or a loading skeleton (import flow, dashboard charts) — build once, centrally.
- **`KeyboardHint`**: a shared component to replace the "Premi N" / "Ctrl+Invio" 9px gray spans (established finding #9) — needed by DashboardAndCeilings (home) and DayLifecycle (`day/new`), currently duplicated ad hoc.
- **Decision needed from the lead before other areas build far**: which of the three visual directions, since type choice (system/Plex Sans/Plex Mono), color hierarchy, and density all cascade into every component above.
