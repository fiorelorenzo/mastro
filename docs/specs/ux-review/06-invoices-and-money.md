# Invoices, Payment, Ageing and Reminders

## What is there now

**`/invoices` — the ageing list** (`src/routes/invoices/+page.svelte`, `+page.server.ts`). Titled "Fatture non pagate" / "Unpaid invoices" (`invoices_heading`). Server loads `listUnpaidInvoices()` (`src/lib/server/repositories/invoice.ts:222-239`, an `isNull(invoice.paidOn)` filter — there is no code path to see a paid invoice here), recomputes `daysLate` against `new Date()` and sorts most-overdue-first. Two `<dl>` summary stats sit above a six-column `RecordList` table (Number, Client, Due date, Status, Days billed, Total). Screenshots: `invoices` in all four passes — two rows, `2026/011` at "In ritardo di 34 giorni" and `2026/015` at "Scade tra 3 giorni", rendered in identical plain black text.

**`/invoices/new` — manual creation** (`src/routes/invoices/new/+page.svelte`, `+page.server.ts`, `src/lib/server/repositories/invoice-form.ts`, `invoice.ts:createInvoice`). Two-step form: a `GET` step picks a contract (`?contractId=`) and loads that contract's eligible unbilled days; once chosen, a second, long `POST` form appears with ~14 document-level fields (number, dates, currency, tax treatment code, statutory-reference language + text typed by hand, stamp duty, social charge, payment method, IBAN, transmission id) and six always-rendered blank line slots, each with its own description/quantity/unit price/amount/tax-rate inputs and a full checkbox list of every eligible day. Screenshot `invoice-new`: before a contract is picked, the entire page is one `<select>` and one button on an otherwise empty 1440×900 canvas.

**`/invoices/[id]` — the document of record** (`src/routes/invoices/[id]/+page.svelte`, `+page.server.ts`). A `<dl>` of document fields (issue/due date, taxable amount, tax amount, optional stamp duty/social charge, total, optional tax treatment code, optional `LegalText` statutory annotation, payment method, IBAN), then four `Section`s: Payment (a paid line or a `<details>` "mark paid" form), Lines, Days it bills, Rebilled expenses — each a `RecordList`. The header's only action is "Prepara un sollecito" / "Draft a reminder", shown only when `data.overdue` is true. Screenshots: `invoice-detail` (paid, `2026/014`) and `invoice-overdue` (`2026/011`, 34 days late) across all four passes.

**`/invoices/[id]/remind` — dunning compose** (`src/routes/invoices/[id]/remind/+page.svelte`, `+page.server.ts`, `src/lib/server/mail/{dunning,render,placeholders}.ts`, `src/lib/server/repositories/dunning-form.ts`). Guards the invoice as overdue before rendering anything (`loadOverdueInvoice`, `+page.server.ts:23-33`); picks from the contract's own `days_after_due`-triggered templates; a `preview` action renders real subject/body against `buildDunningContext` (real total, due date, days late, and the actual billed-day register — `dunning.ts:52-81`, `render.ts:45-64`) in the _contract's_ `templateLanguage`, never the operator's interface locale; a `send` action dispatches through the same `dispatchEmail` every other compose screen uses. Screenshot `invoice-remind`: for the seeded overdue invoice with no template yet, a clean "this contract has no reminder template yet, create one" empty state with a working link.

**Money formatting** (`src/lib/i18n/format.ts`, `src/lib/money.ts`). Every amount is `MinorUnits` (a branded integer, cents) routed through `formatMinorUnits` → `Intl.NumberFormat(locale, {style:'currency'})`; nothing hand-rolls a separator or a `toFixed`. `RecordList`'s table CSS sets `font-variant-numeric: tabular-nums` and right-aligns `end` columns (`src/lib/layout/RecordList.svelte:82-100`). This part is genuinely solid — see "what to keep" below.

## What is wrong

1. **BLOCKER — a legally significant total is built from three independently hand-typed numbers with zero reconciliation.** `parseInvoiceForm` (`src/lib/server/repositories/invoice-form.ts:132-152`) reads `quantity`, `unitPrice` and `amount` as three separate free-text fields; `createInvoice` (`src/lib/server/repositories/invoice.ts:84-87`) sums the typed `amount` values directly into `taxableAmount` — it never checks `amount ≈ quantity × unitPrice`, and nothing checks that `quantity` matches `workUnitIds.length` (the number of days actually ticked, `invoice-form.ts:118`). An operator can check 4 day boxes, type quantity `10`, unit price `620`, and amount `3150`, and the invoice will save with no warning. For a product whose stated job is "no ceiling crossed blind," the one number that actually goes on the bill is unverified. Screenshot: `invoice-new`.
2. **BLOCKER — an imported invoice's archived original is stored but unreachable from the UI.** The `document` table already links an imported invoice to its source bytes (`ownerType: 'invoice', ownerId: invoiceRow.id`, written in `src/lib/server/import/persist.ts:203-213`, read back for dedup in `src/lib/server/repositories/invoice.ts:264-267`). But `getInvoiceWithLines` (`invoice.ts:152-196`), the query the detail page runs, never joins `document`, and `src/routes/invoices/[id]/+page.svelte` has no "view original" affordance anywhere. This directly breaks the product invariant "every derived datum keeps its source document" at the one screen that is supposed to be the document of record.
3. **BLOCKER — named cause of the mobile overflow.** `invoice-detail` and `invoice-overdue` measure 410px of content in a 390px viewport (`/tmp/shots/report.json` mobile-it: `"cw": 390, "sw": 410, "ovf": true` for both). Cause: `src/routes/invoices/[id]/+page.svelte:114` — `<dl class="grid grid-cols-2 gap-x-4 gap-y-2 text-sm">` — a fixed 50/50 grid with no `min-width: 0` and no word-break on `<dd>`. The IBAN value `IT60X0542811101000000123456` (27 characters, zero spaces — an unbreakable token) forces its column past the available track width, blowing the whole grid, and with it the page, past the viewport edge. **The fix already exists twice in this codebase** — `src/routes/day/[id]/+page.svelte:60` and `src/routes/proposals/[id]/+page.svelte:30` use exactly this pattern for the same problem: `grid-cols-[max-content_1fr] gap-x-4 gap-y-2 text-sm [&_dd]:min-w-0 [&_dd]:break-words`. Copying those three classes onto the invoice-detail `<dl>` removes the overflow.
4. **MAJOR — ageing severity is discarded, not just unstyled.** `ageingStatus(daysLate)` (`src/routes/invoices/status.ts:15-24`) returns `{ level: StatusLevel, label: string }` — precisely the shape `StatusIndicator` (`src/lib/design/charts/StatusIndicator.svelte`) needs, already used for exactly this kind of severity elsewhere (`CeilingMeter.svelte:76`, `OfflineDataBanner.svelte:33`). But both call sites here — the list's Status column (`invoices/+page.svelte:32`, with a comment acknowledging the icon was dropped) and the detail subtitle (`invoices/[id]/+page.svelte:23`) — read only `.label`, because `RecordColumn.format` is typed `(row) => string` (`src/lib/layout/types.ts:13`): there is structurally no way to put a colored, iconed status in a `RecordList` cell today. Result: "In ritardo di 34 giorni" and "Scade tra 3 giorni" render in identical black text at identical weight (screenshots: `invoices`, all four passes). A day-ledger that promises nothing goes unnoticed cannot rely on the reader parsing prose to tell "34 days late" from "fine."
5. **MAJOR — unpaid-only list with no way to see, filter, or search anything else.** `/invoices` hard-codes `listUnpaidInvoices()`; there is no "paid" view, no status filter, no sort, no search, no date-range. Once an invoice is paid it drops out of the only list screen entirely — the sole way to find it again is to already know its UUID (typed into the URL) or to drill through the client/contract. For "money the consultant actually collected," the product currently has no answer.
6. **MAJOR — an unactionable reminder renders a bare, chromeless "400."** `loadOverdueInvoice` (`src/routes/invoices/[id]/remind/+page.server.ts:23-28`) calls `error(400, m.mail_dunning_not_overdue())` for a paid or not-yet-due invoice. There is no `+error.svelte` anywhere under `src/routes` (confirmed by a full-tree search) — not at the route, not at the app root — so this bubbles to SvelteKit's built-in error page: no sidebar, no header, no locale switch, literally the digits "400" as the page's only heading. The same failure class already exists one level up: the detail page's own loader throws `error(404, m.invoice_not_found())` (`invoices/[id]/+page.server.ts:10`) for any bad id, with the identical bare-page consequence. Today this needs a stale link/bookmark to reach in practice — but the detail page's "Prepara un sollecito" link is conditionally rendered only while `data.overdue` is true, so a link saved or shared _before_ payment was recorded (e.g. from an alert, once alerts start linking to invoices) becomes a dead end with no way back except the browser's own back button.
7. **MAJOR — the single most consequential action on an overdue invoice has the least visual weight.** "Prepara un sollecito" / "Draft a reminder" (`invoices/[id]/+page.svelte:102-106`) is a plain underlined text link in the page-header actions slot — visually indistinguishable from the "Fatture non pagate" breadcrumb sitting directly above it. On the one page in the product where a human is expected to notice "this is 34 days late, do something," the thing to do is styled like a footnote.
8. **MAJOR — the legally-verbatim statutory text is retyped by hand with no source of truth offered.** `invoices/new`'s "Testo del riferimento normativo" / "Lingua del riferimento normativo" (`invoices/new/+page.svelte:152-171`) are freeform inputs. The exact strings the law requires already exist as data in the active jurisdiction pack, keyed by tax treatment (`src/lib/server/fiscal/packs/it-flat-rate.ts:90-93,123-126,156-159`, `it-standard.ts:52-55`, each built through the sanctioned `legalText()` constructor). Nothing on the form offers, suggests, or cross-checks against these. A transcription slip in a string invariant 5 requires to render verbatim is invisible to the form and to the reader (`LegalText.svelte` renders whatever it's given, correctly, without judging it).
9. **MINOR — the first Section on the page has no top spacing.** `Section.svelte`'s spacing rule is a sibling selector, `.section + :global(.section) { margin-top: 2rem }` (`src/lib/layout/Section.svelte:26-28`) — it only fires between two consecutive Sections. The field `<dl>` before the first Section ("Payment"/"Pagamento") is not itself a `.section` and carries no bottom margin, so the IBAN row and the "Payment" heading sit almost flush against each other. Visible in every `invoice-detail`/`invoice-overdue` screenshot, all four passes.
10. **MINOR — paid and overdue are indistinguishable at a glance.** Beyond the subtitle text and which action/disclosure shows, the invoice detail header carries no color or badge difference between "Pagata" and "In ritardo di 34 giorni" (screenshots: `invoice-detail` vs `invoice-overdue`, same layout, same weight). A 34-day-late document of record should look different from a settled one before the reader gets to the words.
11. **MINOR — the headline total has no typographic weight.** `invoice.total` (`invoices/[id]/+page.svelte:144`) is `font-semibold` at the same `text-sm` as every other field in the `<dl>` — the one number a document of record exists to state clearly is not visually the biggest thing on the page.
12. **MINOR — "Invia" carries no more weight than "Anteprima."** Both dunning buttons share `class="border px-4 py-2 text-sm"` (`remind/+page.svelte:75-77,98-100`); Send adds only `font-semibold`. Sending drafts and dispatches a real, worded email citing a real balance and a real days-late figure to the client — the UI treats it like any other bordered button.
13. **MINOR — invoice creation shows six blank line slots regardless of how much is actually eligible.** `invoices/new/+page.svelte:49-51,202-265` always seeds `lineSlots` to six empty rows and repeats the _entire_ eligible-days checkbox list under every one of them, even for a contract with a single unbilled day. Long, repetitive scroll for the common case.
14. **POLISH — `wide` page width is unused space here today.** `/invoices` uses `Page ... width="wide"` (72rem, `invoices/+page.svelte:50`) for a 2-row, 6-column table that occupies roughly 40% of a 1440px canvas (screenshot `invoices`, desktop passes) — same pattern the lead already flagged for the calendar; worth keeping in mind when this list gains ageing-bucket grouping (finding below) rather than dropping `wide` outright, since a real invoice count plus a Stato column with an icon will use the width.

## Options

### `/invoices` (the ageing list)

- **A. Restyle in place.** Swap the Status column's plain text for `StatusIndicator` (needs the `RecordColumn` extension in Cross-cutting asks), add a "Mostra pagate" toggle that switches the query, keep everything else. Effort S. Risk low. Does not fix: no unified paid+unpaid ledger view, no sort/filter, no ageing grouping.
- **B. Restructure the page.** Add a status filter (segmented control or dropdown: Non pagate / Tutte / Pagate) backed by a new `listInvoices({ status })` repository function; group unpaid rows under ageing-band subheadings (Scadute da oltre 30gg / Scadute / In scadenza entro 7gg / A scadere) each carrying a colored `StatusIndicator` heading and a running subtotal; make Due date / Total sortable. Effort M. Risk medium (new repository function, i18n keys ×2, tests for the grouping boundary). Unlocks an actual ageing view the consultant can act on in seconds, and a real record of what got paid.
- **C. Rethink the flow.** Fold `/invoices` into a broader billing worklist: the ageing table plus an inline "record payment / remind" action per row (no page navigation for the two-click cases) plus a compact issued-vs-collected-vs-overdue strip reusing the existing chart engine. Effort L. Risk high (inline mutation UX, cross-cutting with Dashboard's territory).
- **Recommendation:** B. It answers "what needs attention" and "what did I already collect" without inventing new interaction patterns or reaching into Dashboard's scope; C is worth revisiting once the design system defines inline-action patterns.

### Invoice detail

- **A. Restyle in place.** Fix the mobile overflow (the named `grid-cols-[max-content_1fr]` + `min-w-0` + `break-words` fix), add spacing before the first Section, add a colored status badge next to the invoice number reusing `StatusIndicator` (good=Paid, warning/serious/critical=overdue bands, neutral=not yet due), give `Totale` a distinct headline style. Nothing else moves. Effort S. Risk low. Does not fix: missing source document, thin/buried action set (mark-paid behind a `<details>` toggle, no dispute, no export).
- **B. Restructure the page.** Header card: number, parties, status badge, headline total. A visible actions rail (not a details-toggle) offering Record payment / Draft a reminder / Dispute / Export, each shown or disabled per state instead of only conditionally rendered; a "Documento originale" link whenever a `document` row exists for this invoice (new repository read, `listDocumentsForOwner('invoice', id)`); "Dispute" wired to the state machine's existing `disputed` work-unit state (already modeled — `register.ts:9` treats a disputed day as "invoiced, then disputed," so the affordance closes a real gap, not a new concept). Effort M. Risk medium (one new repository call, one new action, states that are modeled in the DB but not yet surfaced). Unlocks turning this from a field dump into a true document of record with full provenance and one visible action set.
- **C. Rethink the flow.** Generate a canonical print/PDF view from the same data as "the document of record," and let the in-app page become purely an actions-and-audit console (payment, remind, dispute, links to the source document and the day register). Effort L. Risk medium-high (new rendering pipeline that must stay faithful to any imported original it's meant to represent).
- **Recommendation:** B. It closes the two proven, evidenced defects (mobile overflow, unreachable source document) and turns four inconsistent affordances into one visible rail, without committing to a PDF pipeline most invoices don't need since the real original is usually already archived.

### Invoice creation (`/invoices/new`)

- **A. Restyle in place.** Keep the bordered-input aesthetic; shrink blank line slots to match what's actually eligible instead of a fixed six; add a client-side running total (sum of typed amounts vs. expected taxable/tax/total) that visibly disagrees before submit. Effort S/M. Risk low. Does not fix the deeper problem: quantity, unit price and amount stay three independently-typed numbers, and the empty first screen remains.
- **B. Restructure the page.** After a contract is chosen, auto-generate one line per rate card in play with quantity pre-filled from the checked days, unit price from the rate card, and amount computed read-only (with an explicit "override amount" escape hatch for the legitimate rounding/discount case `invoice_line.amount`'s own schema comment anticipates); offer tax treatment + statutory text as a picker sourced from the active jurisdiction pack's treatments, keeping the current freeform fields as a manual fallback for a document that doesn't match a modelled pack entry. Effort M/L. Risk medium (new repository read exposing pack treatments to the route; cross-checks added to `invoice-form.ts`). Unlocks: turns three hand-typed numbers and a hand-copied legal citation into one pre-populated, verifiable line.
- **C. Rethink the flow.** A three-step wizard: (1) pick contract + days, with a running total shown as days are checked; (2) confirm/adjust document fields, tax treatment sourced from the pack; (3) a full preview shaped exactly like the detail page before creating. Effort L. Risk medium (new multi-step route, more state threaded through form actions).
- **Recommendation:** B. It removes the riskiest gap — unreconciled totals and a hand-copied legal citation — in one page instead of three; C is the natural longer-term destination once the design system has stepper/wizard patterns.

### Reminders (`/invoices/[id]/remind`)

- **A. Restyle in place.** Replace the bare `error(400, …)` with a proper `+error.svelte` (route-level or app-root) that keeps sidebar/header and states the specific reason with a link back to the invoice; give "Prepara un sollecito" visual weight matching its consequence; differentiate "Invia" from "Anteprima" once the design system defines emphasis levels. Effort S. Risk low. Does not fix the root cause: the guard condition still throws instead of returning a normal state.
- **B. Restructure the page.** Stop `loadOverdueInvoice` from calling `error()` for "not yet due" or "already paid" — have the load return `{ reason: 'not_yet_due' | 'paid' | 'ok', … }` and render an explanatory empty state, following the pattern this same screen already gets right for "no template yet" (`remind/+page.svelte:45-54`, with its working "create one" link). Effort S/M. Risk low (pure refactor of an existing guard, no schema change). Unlocks a reusable "action unavailable for this record's state" pattern the invoice-detail options above (e.g. "dispute" on a paid invoice) can reuse.
- **C. Rethink the flow.** Not proposed — the preview → send flow itself, scoped to the invoice's own contract templates, real figures, correct target language, is sound and matches "agents propose, humans confirm."
- **Recommendation:** B. Small, low-risk, and forecloses the entire bare-error-page failure class (this one plus the identical `invoice_not_found` 404 on the detail page) instead of only dressing up this one instance.

## Cross-cutting asks

- **`RecordColumn` rich-cell support** (`src/lib/layout/types.ts`): add an optional `render` snippet alongside the existing `format: (row) => string`, so `RecordList` can host `StatusIndicator` (or any small component) in a cell while keeping its dual table/card rendering and accessibility guarantees (unique keys, `sr-only` caption) unchanged for every existing caller. First consumer: the invoices Status column. Any screen with a per-row status (proposals, alerts, day states) benefits identically.
- **A field-list primitive** that bakes in `grid-cols-[max-content_1fr] gap-x-4 gap-y-2 [&_dd]:min-w-0 [&_dd]:break-words` by construction (e.g. `<FieldList>` in `$lib/layout`), instead of `day/[id]`, `proposals/[id]`, and (once fixed) `invoices/[id]` each hand-writing the same Tailwind incantation — so a fourth `<dl>` can't reintroduce this overflow.
- **A generic error boundary** (`+error.svelte`, at least app-root) that keeps app chrome and renders `error()`'s message legibly. Needed by more than this area: `invoices/[id]` alone throws both a 404 (`invoice_not_found`) and, via the remind sub-route, a 400 (`mail_dunning_not_overdue`) with the same bare-status-code consequence today.
- **A "not available in this state" empty-state pattern** (reason + explanation + link back), generalizing the reminder screen's own good "no template yet" state, for every "this action doesn't apply to this record right now" case — reminders on a non-overdue invoice today, dispute-on-a-paid-invoice tomorrow.
- **Button hierarchy (primary/secondary/emphasis)** — already flagged at the program level; this area specifically needs it for "Invia" vs "Anteprima," "Segna come pagata," and "Prepara un sollecito" so the weight of an action matches its consequence.
- **A headline-amount typographic style** distinct from body text/`font-semibold`-at-`text-sm`, for the one total that matters on an invoice, expense, or rate-card screen.
