# Clients & Contracts

## What is there now

**Clients list** (`/clients`, `src/routes/clients/+page.svelte`) is a five-column `RecordList` — Ragione sociale, Codice fiscale, Paese, Canale di comunicazione, Contatti — with the legal name as the row link and a single "Nuovo cliente" text-link action top-right. Three rows in the seed, all Italian, all "Email" channel, all "0" contacts. Screenshot: `desktop-it/clients.png`.

**Client form**, shared by `/clients/new` and `/clients/[id]/edit` as `ClientForm.svelte`: four `<fieldset>`s — Identità legale (Ragione sociale, Codice fiscale, Partita IVA, Paese; 4 inputs), Sede legale (5 address inputs), Comunicazioni (1 select), Contatti (a hard-coded 4 blank contact cards × 5 fields = 20 inputs, `ClientForm.svelte:9-11,123-158`). Total 30 inputs + 1 hidden `contactCount` = 31, all in one unbroken column, no default values except an empty string per field. `parseClientForm` (`client-form.ts`) validates legal name/tax id/country/address line 1/city/postal code/notice channel as required, treats a contact row with no name as a silently-dropped spare slot. Screenshots: `desktop-it/clients-new.png` (2149px, per the task brief), `desktop-it/client-edit.png`, `mobile-it/clients-new.png`.

**Client detail** (`/clients/[id]/+page.svelte`) is a title + subtitle (tax id · channel), an "Identità legale" `<dl class="grid grid-cols-2">` (tax id, VAT if present, country, channel, address as one run-on `<dd>`), a conditional "Contatti" `<ul>` (hidden entirely when empty — true for all three seed clients), and a "Contratti" section using `RecordList` (title/status/starts-on/renewal-type). One "Modifica" text link top-right, one "Nuovo contratto" text link on the Contratti section. Screenshot: `desktop-it/client-detail.png`.

**Contract form**, shared by `/contracts/new` and `.../[contractId]/edit` as `ContractForm.svelte`: four fieldsets — Identità (title, signed-document reference, status, template language; 4), Durata e rinnovo (starts-on, ends-on, renewal type, [renewal-notice-days if type≠none], termination-notice-days; 4–5), Pagamento (payment-terms kind, [net-days xor day-of-month], invoicing cadence, currency, tax treatment; 5), Approvazione e spese (requires-prior-approval checkbox, expense-policy kind, [cap amount if kind=reimbursed_with_cap], [pre-authorisation checkbox if kind≠not_reimbursed]; 2–4). Conditional fields are driven client-side with `$state` bindings (`ContractForm.svelte:30-32`), the same pattern the day form uses — no round trip needed to reveal them. `/new`'s defaults (`renewalType: 'none'`, `paymentTermsKind: 'net'`, `expensePolicyKind: 'not_reimbursed'`, `requiresPriorApproval: false`, `templateLanguage: 'en'`, `status: 'draft'`, `currency: 'EUR'`, `invoicingCadence: 'monthly'`) produce exactly 15 visible inputs; the seeded contract's edit state (renewal type `explicit`, expense policy `reimbursed_at_cost`) produces 17. `parseContractForm` (`contract-form.ts`) mirrors every conditional branch and re-validates it server-side. Screenshots: `desktop-it/contract-new.png`, `desktop-it/contract-edit.png`, `mobile-it/contract-new.png`.

**Contract detail** (`.../[contractId]/+page.svelte`) is the densest page in scope: title + subtitle (starts-on · renewal type · notice period), then five sections — Identità (merged status+term dl, 6–8 rows), Note sulle clausole (4-column table: reference/verbatim/interpretation/notes), Pagamento (4-row dl), Approvazione e spese (3-row dl), Listini (3-column `RecordList`), Spese (5-column `RecordList` plus a hand-rolled rebill mini-form for reimbursable, not-yet-rebilled rows). Every section action ("Nuovo listino", "Nuova spesa", "Aggiungi nota sulla clausola") and the page action ("Modifica contratto") is an underlined text link. The rebill affordance sits below the Spese table as a `<ul>` of one-line forms, each repeating the date and description of the row above it, a native `<select>` of open invoice lines, and a small submit button (`+page.svelte:312-331`). The loader (`+page.server.ts:25-30`) fetches rate cards, clause notes, expenses and invoice lines (for the rebill picker only) — never `work_unit`/day records, never invoices themselves. Screenshots: `desktop-it/contract-detail.png`, `mobile-it/contract-detail.png`, `dark-it/contract-detail.png`.

**Rate card form** (`RateCardForm.svelte`, `.../rate-cards/new` and `.../[rateCardId]/edit`): valid-from date (required), valid-to date (optional, hint "leave blank for the current, open-ended card"), kind select, amount (plain text), unit select, allowed-fractions text (hint gives an example), then conditionally minimum-hours (kind=hourly) or disbursement-period select (kind=fixed_recurring). `parseRateCardForm` checks decimal shape with a dot-only regex and leaves overlap detection entirely to the database's exclusion constraint, caught after submission (`rate-card-form.ts:37-41`). Screenshot: `desktop-it/rate-card-new.png`.

**Expense form** (`ExpenseForm.svelte`, `.../expenses/new` and `.../[expenseId]/edit`): date, description, amount (plain text, no format hint), pre-authorised checkbox gating a conditional authorisation-reference field, and a receipt upload (native `<input type="file">` + confidential checkbox) that only appears when no receipt is on file yet, since a receipt is immutable once ingested. Screenshot: `desktop-it/expense-new.png`.

**Clause note form** (`ClauseNoteForm.svelte`, `.../clause-notes/new` and `.../[clauseNoteId]/edit`): four fields, all but the reference a `<textarea>` — clause reference, verbatim text, interpretation adopted, free notes. The schema's own doc-comment (`clause-note.ts:6-21`) states the intent explicitly: notes belong "next to the fields the note affects," on the contract's own screen, deliberately not behind a tab, because "the contract detail screen has no tabs to bury a note in." Screenshot: `desktop-it/clause-note-new.png`.

## What is wrong

1. **[BLOCKER — does not work]** Every amount field in this territory silently rejects the decimal format the rest of the app displays everywhere (`700,00 €`, `46,00 €` in `contract-detail.png`). `decimalStringToMinorUnits`'s regex (`src/lib/server/import/decimal.ts:12`, `/^(-?)(\d+)(?:\.(\d+))?$/`) and `parseRateCardForm`'s own check (`rate-card-form.ts:28`, `/^-?\d+(\.\d{1,2})?$/`) accept only a literal dot; typing the Italian-natural `46,00` throws and surfaces as a bare "Importo non valido"/"Importo non valido" with no format hint anywhere near the field (`ExpenseForm.svelte:34-37`, `RateCardForm.svelte:55-59`, `ContractForm.svelte:256-267` all have label+input+error, no hint). A product whose promise is "no ceiling crossed blind" cannot have its own money-entry fields reject the way a consultant naturally types money.

2. **[BLOCKER — cannot be found, and design invites the miss]** `requiresPriorApproval` — the one checkbox that operationalizes "a day must be approved before it's worked" — defaults to unchecked on every new contract (`contracts/new/+page.svelte:24`) and is visually identical in weight to every other checkbox on the page (`ContractForm.svelte:233-236`, no accent, no consequence copy). A contract can go live with the product's central protection silently off, and nothing on the form or the detail page calls that out.

3. **[BLOCKER — cannot be found]** The contract's own detail page shows no days and no invoices. The loader (`+page.server.ts:25-30`) queries rate cards, clause notes, expenses and invoice-lines-for-rebilling only — never `work_unit` or `invoice`. To check "is every worked day on this contract approved and paid," a consultant must leave the page and manually filter the global day calendar and invoice list, neither of which currently accepts a `contractId` filter. This is the one page whose entire reason to exist is answering that question for one contract.

4. **[MAJOR — ugly, and wastes the 30-second budget on the wrong task]** The client form pre-renders four full blank contact cards (20 of its 31 inputs) regardless of how many contacts a client actually has — all three seeded clients have zero (`clients.png`, `Contatti: 0`). `canApprove`, the field the whole approval chain depends on, is the fifth and smallest control in each card (`ClientForm.svelte:153-156`), no more prominent than "Ruolo."

5. **[MAJOR — ugly]** All three multi-field forms present every field as an equal-weight row inside a fieldset named after a database concept, labelled from the column name (`contract_form_tax_treatment_label` → "Codice del regime fiscale", `contract_form_renewal_notice_days_label` → "Preavviso di rinnovo (giorni)"). `templateLanguage` and `status` — administrative metadata nobody needs to understand the deal — sit in the same fieldset and at the same visual weight as `title`.

6. **[MAJOR — does not work at the viewport the product claims to support]** Two incompatible "key/value list" implementations coexist. `RecordList`'s card mode (`RecordList.svelte:101-128`) is a flex row — a long label wraps onto its own lines while the value keeps its natural width. The ad hoc `<dl class="grid grid-cols-2 gap-x-4 gap-y-2">` used directly in `client/[id]/+page.svelte:56` and three times in `contracts/[contractId]/+page.svelte:161,217,237` is a rigid 50/50 grid with no responsive override, so at 390px an Italian label like "Richiede la pre-autorizzazione per le spese rimborsabili" is squeezed into a ~45%-width column and wraps three lines while its answer ("No") sits stranded on the other half (`mobile-it/contract-detail.png`).

7. **[MAJOR — cannot be found until it's too late]** Rate cards render as a flat table row ("1 gen 2026 – aperto") with nothing marking which card is in force today, and the database's own guarantee that two cards can never overlap (`rate_card_no_overlapping_validity`) is invisible in the UI until it comes back as a `23P01` after submission (`rate-card-form.ts:37-41`). The rule is real and enforced — the form just never tells you about it until you've already broken it.

8. **[MAJOR — ugly, confusing]** The expense-rebill affordance duplicates the row it targets. The pending-rebill list repeats the exact date and description already shown in the table row directly above (`contracts/[contractId]/+page.svelte:312-331`), visible in `contract-detail.png` as two consecutive "14 lug 2026 — Treno Milano — Verona" lines — a workaround for `RecordList` having no row-scoped action slot, not a designed affordance.

9. **[MAJOR — silent wrong default]** `templateLanguage` defaults to `'en'` on every new contract (`contracts/new/+page.svelte:28`) with no relation to the client's own country. Every seeded client is Italian; a template-language default that ignores the client record produces contracts whose generated documents render in the wrong language unless the drafter remembers to change one of fifteen fields.

10. **[MAJOR — cannot be found]** Neither the client list nor the client detail page shows anything financial: no unpaid total, no days-this-year, no concentration-vs-cap figure, no last-approval-received date. `clients/+page.server.ts` and `clients/[id]/+page.server.ts` query only client/contacts/contracts. For a one-person consultancy, "which clients need my attention" _is_ the point of looking at this screen, and it currently answers only "what is this client's postal address."

11. **[MINOR — evidence with no timestamp]** Clause notes render as a plain table row with the verbatim text wrapped in ASCII quotes inline (`+page.svelte:82`) and no recorded-on date, even though `clauseNote.createdAt` is fetched by every call to `listClauseNotes` (`clause-note.ts:14-17`) and exists on every row. A record meant to resolve a future dispute by "rereading a decision instead of re-guessing one" (the schema's own words) doesn't say when the decision was made.

12. **[MINOR — ugly]** "Note libere" is an always-rendered table column, empty for the only seeded row (`contract-detail.png`). Harmless with one row; on a contract with several clause notes and only one carrying a free note, most of the column reads blank.

13. **[MINOR — ugly]** Every section action ("Nuovo contratto", "Nuovo listino", "Nuova spesa", "Aggiungi nota sulla clausola") and the page-level "Modifica"/"Modifica contratto" is an underlined text link, visually identical to the breadcrumb links above them.

14. **[POLISH]** Page titles built by string concatenation overflow their own space at normal lengths: "Nuova nota sulla clausola per Contratto quadro 2026 — piattaforma logistica" wraps two lines and is still truncated at 70 characters in the accessibility check (`report.json`), and repeats the full contract title on all six of that contract's child create/edit pages.

15. **[POLISH]** The expense receipt upload is a bare native `<input type="file">` reading "Choose File No file chosen" in English on an Italian page (`expense-new.png`), with no design-system treatment.

## Options

### Client form (new/edit)

- **A. Restyle in place** — Keep the four fieldsets; collapse Contatti to one visible card + "Aggiungi contatto" instead of four blank ones; default `noticeChannel` to `email` (the channel every seeded client already uses); add a visible optional-field marker (e.g. "(facoltativo)" suffix on Partita IVA / Indirizzo riga 2 / Regione) instead of relying on invisible `required`. Effort: S. Risk: low. Does not fix: the form is still one long unbroken scroll, and field labels stay column-name literal.
- **B. Restructure the page** — Turn the four fieldsets into `Section`/`Card`-weighted blocks (matching the pattern contract detail already uses), with Contatti as a collapsed-by-default disclosure (it's the only genuinely variable-length part) opened on demand or when editing a client that already has contacts. Effort: M. Risk: low–medium (needs an accessible disclosure component from the design system).
- **C. Rethink the flow** — Allow saving a client with only legal name/tax id/country/notice channel, deferring address and contacts to an explicit "complete later" path, mirroring how an ACP proposal already creates partial records from evidence before a human fills in the rest. Effort: L (relaxes several currently-hard-required fields and touches every downstream reader that assumes a complete address — invoices, mail templates). Risk: high.
- **Recommendation**: A now — it removes 15 of the form's 31 fields for the common zero/one-contact case at low cost — then B once volume justifies the visual weight of section boundaries.

### Client list

- **A. Restyle in place** — Swap the low-value "Contatti" count column for one financial fact (e.g. unpaid total or active-contract status). Effort: S. Risk: low. Does not fix: still no concentration/exposure picture.
- **B. Restructure the page** — Add Unpaid total, Days this year, Last approval received, reusing the same per-client revenue helpers the dashboard's concentration chart already calls (`fiscal/revenue.ts`'s `fetchClientRevenueBreakdown`), scoped per row instead of aggregated once. Effort: M (query reuse, not a new subsystem). Risk: medium (wider table; use `Page`'s existing `wide` variant).
- **C. Rethink the flow** — Reorder the list by attention needed (clients with an overdue invoice or unapproved day surface first, with a status chip). Effort: L. Risk: higher — introduces implicit priority logic; a plain sortable table stays more auditable for evidence-grade data.
- **Recommendation**: B — the underlying computation already exists for the dashboard; this is a reuse job that turns an address book into the screen the product's own brief says a one-person consultancy needs.

### Client detail

- **A. Restyle in place** — Replace the raw `<dl class="grid grid-cols-2">` with the shared key-value component (see Cross-cutting asks); add a compact "This year" strip above Contratti (unpaid, days worked, last approval) sourced the same way as the list. Effort: S–M. Risk: low.
- **B. Restructure the page** — Add a per-client concentration fact: this client's share of total revenue against any active concentration-cap clause on their contracts, reusing `fetchClientRevenueBreakdown` scoped to one client, rendered as a single ceiling-style bar rather than a paragraph of numbers. Effort: M, depends on a shared ceiling/share-meter primitive. Risk: medium (blocked on that primitive landing).
- **C. Rethink the flow** — For clients with exactly one contract (common early on), merge client + contract into one screen to save a click. Effort: M. Risk: medium–high — introduces a cardinality branch nowhere else in the app special-cases.
- **Recommendation**: B — the exposure figures are the single biggest gap this brief identifies, and the computation already exists; C trades consistency for a click that isn't the product's actual bottleneck.

### Contract form (new/edit)

- **A. Restyle in place** — Keep the four fieldsets and the existing `$state`-driven conditional fields (this part is already right — keep it); flip `requiresPriorApproval`'s default to checked with a one-line consequence hint under it; default `templateLanguage` from the client's country instead of a hardcoded `'en'`; give `taxTreatment` a datalist of the active jurisdiction pack's known codes instead of a bare free-text guess. Effort: S–M. Risk: low. Does not fix: fields still read in undifferentiated DB-column order.
- **B. Restructure the page** — Regroup into Basics (title, starts-on, currency, cadence, payment terms) / Duration & renewal (progressive-disclosure on renewal type) / Approval & expense policy (visually promoted — bordered/accented, since it's what the product's promise hinges on) / Administrative metadata (status, signed-doc reference, template language — demoted into a collapsed "Details" disclosure). Effort: M. Risk: low–medium.
- **C. Rethink the flow** — Offer an "engagement type" chooser at the top (day-rate / continuous / retainer — the three archetypes the seed data itself models) that pre-sets sensible defaults and hides fields that archetype never uses, while remaining fully editable. Effort: L. Risk: medium — a wrong guess must never hide a field the user actually needs.
- **Recommendation**: B — direct, low-risk fix for the brief's central complaint about this form, and it makes the approval checkbox the thing you see first instead of the thing you might miss.

### Contract detail

- **A. Restyle in place** — Keep the current five-section-plus-two-tables structure; replace the rebill shadow-list with a proper row action inside the Spese `RecordList`; add an "in force" marker to the current rate card row; show `createdAt` on clause notes; swap every raw `<dl>` for the shared key-value component; replace underlined action links with the design system's button component. Effort: M. Risk: low — doesn't touch information architecture. Does not fix: the page still cannot answer "is every day on this contract covered" or "what have I invoiced against it" — those facts remain entirely absent.
- **B. Restructure the page** — Reorganize around three questions: _What are the terms_ (the existing static-fact sections, kept compact); _What is my exposure right now_ (a new summary strip: current rate card in force, days-this-year by state pulled from `work_unit` filtered by `contractId`, sourced the same way the dashboard's ceiling data already is); _What is billable and pending_ (rate cards, expenses, **and invoices raised against this contract**, adjacent). Clause notes move next to the specific term row they annotate rather than sitting in their own floating section. Effort: L — needs new `contractId`-scoped queries for days and invoices, which don't exist today (coordinate with the day-lifecycle and invoicing areas; this document only specifies the requirement, not the query). Risk: medium. Unlocks the page actually answering "is this contract healthy," the entire reason a contract has its own screen.
- **C. Rethink the flow** — Split into a compact overview plus first-class list pages: `/contracts/[id]` becomes a short summary (terms, rate in force, exposure numbers, contract-specific alerts) linking out to `/rate-cards`, `/expenses`, `/clause-notes`, `/days`, `/invoices` as their own routes (each already has its own create-flow child route today; this promotes the embedded sections to top-level pages). Effort: L. Risk: highest — trades one scroll for several navigations, and works against the clause-note schema's own documented intent ("the contract detail screen has no tabs to bury a note in") — only worth it once a single contract's rate-card/expense history genuinely outgrows one page.
- **Recommendation**: B — it keeps everything on one scroll (matching the app's own stated preference against tabs) while finally answering the two questions the page cannot answer today; revisit C only if real usage shows a single contract's records outgrowing that scroll.

### Rate cards (list on contract detail + new/edit form)

- **A. Restyle in place** — Sort newest-first, add an "in force" badge on the row whose validity spans today, add a one-line static explanation of the exclusion constraint near the Valido dal/Valido al fields, and validate overlap client-side against the already-loaded sibling cards before submit (server constraint stays the final authority). Effort: S–M. Risk: low. Does not fix: still a flat table with no sense of the amount trend over time.
- **B. Restructure the page** — A small end-to-end timeline strip above the table (segments = validity periods, a marker for today), each segment linking to its row. Effort: M. Risk: low–medium (new small chart-adjacent component; coordinate token/shape choices with the design-system palette work).
- **C. Rethink the flow** — Replace "new rate card" with a "change the rate" action that pre-fills `validFrom` the day after the current card's `validTo`/today and shows a before/after amount diff, rather than a blank form disconnected from history. Effort: M. Risk: medium (changes the create entry point's framing, needs care for the very first rate card on a contract, which has no "before").
- **Recommendation**: A first (cheap, removes the "learn the rule by breaking it" problem), B if a contract's rate history in practice grows past 2–3 cards often enough that a flat table stops being legible.

### Expense form

- **A. Restyle in place** — Fix the amount parser to accept the locale decimal separator consistently with `formatAmount`/`formatMinorUnits` (not just add a hint — a hint alone still lets the mistake happen); move the receipt upload above the amount fields, since "is there a receipt" more directly frames "is this reimbursable" than the current order. Effort: S–M (touches `decimal.ts`'s shared regex plus the three per-form `DECIMAL` checks). Risk: low.
- **B. Restructure the page** — Not warranted; this is a small, single-purpose form and a structural rethink adds nothing over A.
- **Recommendation**: A — this is a correctness fix, not a styling one; every amount field in this territory shares the same bug.

### Clause notes (contract-detail section + new/edit form)

- **A. Restyle in place** — Show `createdAt` as a visible "recorded on" fact; render verbatim text as a blockquote rather than an inline-quoted table cell; hide the Note libere column when no row in the set has a note. Effort: S. Risk: low. Does not fix: notes still sit in a floating section, disconnected from the specific field (renewal type, expense policy) they interpret.
- **B. Restructure the page** — Present each note as a card (clause reference as heading, verbatim text as a blockquote, interpretation adopted prominent, recorded-on date, free notes secondary) and anchor it visually to the Identity/Payment/Approval `dt` it modifies via a small footnote marker — realizing the proximity intent already written into the schema's own comment (`clause-note.ts:16-21`) instead of relying on section order alone. Effort: M. Risk: low.
- **C. Rethink the flow** — Add a formal `appliesTo` classifier so a note can programmatically link to the exact field row instead of a human reading the clause reference. Effort: L. Risk: medium — this directly reopens a decision the schema comment says was deliberately _not_ made ("this table carries no `subject`/`appliesTo` classifier of its own"); only take this path if B's visual-only anchoring proves insufficient in practice.
- **Recommendation**: B — it fulfills the documented intent without reopening a data-model decision that was made deliberately.

## Cross-cutting asks

- **Key-value / description-list component.** Replaces every ad hoc `<dl class="grid grid-cols-2">` in this territory (client detail, contract detail ×3) with something that behaves like `RecordList`'s existing card mode: label wraps freely, value keeps a readable width, no rigid 50/50 split. States: default, and a "with source/footnote marker" variant for the clause-note anchoring in Option B above.
- **Money/amount input.** One control, reused by expense amount, rate-card amount, contract expense-cap amount (and eventually invoice line amount): accepts and displays the same decimal separator `formatAmount`/`formatMinorUnits` render everywhere else, shows the currency affix, single parsing rule instead of four independent `<input>`+regex pairs. States: default, error (format), error (validation, e.g. non-positive).
- **Disclosure/accordion primitive.** Needed for the client form's Contatti block, the contract form's "Administrative metadata" group, and any future collapsed section. States: collapsed (with a count badge, e.g. "2 contacts"), expanded, focus-visible on the trigger.
- **Ceiling/share meter.** A bar-plus-reference-line primitive generalized from the dashboard's concentration chart, needed by client detail Option B to show one client's share against their own cap without embedding a full chart.
- **Real button component (primary/secondary).** Replaces every underlined text link used for a create/edit action ("Nuovo contratto", "Modifica", "Aggiungi nota sulla clausola", etc.) across every screen in this document, distinguishing "do something" from "navigate somewhere" (which stays a text link/breadcrumb).
- **Required/optional field convention.** Every form in this document relies solely on invisible HTML `required`; needs one system-wide convention (asterisk, "(optional)" suffix, whichever the design system picks) applied consistently.
- **Styled file input.** Needed for the expense receipt upload; must render its label in the interface locale rather than the browser's own English default.

## Verification notes

- **Screens**: `clients`, `clients-new`, `client-detail`, `client-edit`, `contract-detail`, `contract-new`, `contract-edit`, `rate-card-new`, plus a rate-card-edit view seeded with **two or more validity periods spanning past/current/future** (not present in the current seed) to actually judge "in force today" legibility, `expense-new`/edit with `preAuthorised` toggled both ways, `clause-note-new`/edit.
- **Viewports**: 1440×900 and 390×844 for every screen above — the dl/`RecordList` responsive mismatch (finding 6) and the contact-card weight problem (finding 4) only show clearly at 390px.
