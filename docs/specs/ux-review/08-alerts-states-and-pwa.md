# Alerts, Settings, System & PWA States

## What is there now

**`/alerts`** (`src/routes/alerts/+page.svelte`, `+page.server.ts`) — one flat `<ul>` of active alerts, most-severe-first (`listActiveAlerts`, `engine.ts:112-134`, sorts by `SEVERITY_RANK`). Each row is a plain `<li class="border p-4">`: a `StatusIndicator` (severity glyph + text label), a title, a body sentence, and — if not yet acknowledged — a single `<form>` posting `?/acknowledge` with a button reading "Conferma presa visione"/"Acknowledge". Acknowledging re-detects the alert server-side against the posted key so a stale write is a no-op (`+page.server.ts:31-41`), then writes a severity-rank floor that suppresses the same alert until it gets worse (`state.ts:68-98`). Screenshot: `desktop-it/alerts.png`, `mobile-it/alerts.png`, `dark-it/alerts.png` — two critical alerts, "Giornata lavorata senza approvazione: Contratto quadro 2026" and "Fattura scaduta: 2026/011", each an identical bordered box.

**`/alerts/settings`** (`+page.svelte`) — a push-notification block (subscribe/unsubscribe, with real busy/permission-denied/unsupported/iOS-needs-install states — the one place in this whole area with a working `disabled={busy}` loading treatment), then an 11-row × 2-column `<table>` of checkboxes (`digest_<type>` / `push_<type>`, one row per `AlertType`) under one "Save preferences" button. Screenshot: `desktop-it/alerts-settings.png`.

**`/settings`** (`+page.svelte`) — three sections: Fiscal profile (read-only, "Configurato direttamente nel database; non esiste ancora un'interfaccia per farlo"), Language (`LanguageSwitch`), and a single link to Alert preferences. Nothing else. Screenshot: `desktop-it/settings.png`, `mobile-it/settings.png`.

**`/sign-in`** (`+page.svelte`, `+page.server.ts`) — centered card (`min-h-[80svh] flex flex-col justify-center`): product name, tagline, a deliberately identical rejection message regardless of cause (`sign_in_rejected`, anti-enumeration by design, `+page.svelte:18-27`), a single Google `<a>` (link not form, intentionally — GET keeps the OAuth hop bookmarkable and outside CSRF checks), allowlist note, language switch. Screenshot: `desktop-it/sign-in.png`, `mobile-it/sign-in.png`.

**`/offline`** (`+page.svelte`) — static, prerendered fallback: heading, one explanatory sentence, a "Try again" button (`location.reload()`). Not vertically centered (`mx-auto max-w-2xl p-8`, top-anchored). Screenshot: `desktop-it/offline.png`.

**No `src/routes/+error.svelte` exists anywhere in the app**, and `src/hooks.server.ts` has no `handleError`. Confirmed by direct filesystem search. Every `error(404, …)`/`error(400, …)` thrown across the app (at least 15 call sites: clients, contracts, clause notes, rate cards, expenses, days, invoices, invoice-remind, documents) falls through to SvelteKit's bundled fallback page.

**PWA**: `InstallPrompt.svelte` (Android `beforeinstallprompt` banner + iOS "Add to Home Screen" hint, both bottom-fixed, engagement-delayed 20s, dismissal remembered in `localStorage`), `OfflineDataBanner.svelte` (shows when any on-screen data came from cache and hasn't been revalidated — driven by the service worker's `mastro:data-stale`/`mastro:data-fresh` postMessages and an `x-mastro-cached-at` header, deliberately not gated on `navigator.onLine`), `service-worker.ts` (precaches shell + `/offline`; runtime data cache is stale-while-revalidate; **never** caches a full HTML document — the one rule the file documents extensively — and wipes the data cache the instant a response reveals the session is gone). `git log` shows this layer has already had one real production incident and fix: commit `2988c8f` ("service worker swallowed the redirect to Google… anyone with the worker installed could not sign in at all"), fixed by switching `handleNavigate` to `redirect: 'manual'`. The fix, and the file's own commentary, read as careful, tested engineering (`sw-cache-policy.test.ts`, `freshness-policy.test.ts`, `install-logic.test.ts`).

**Empty states, product-wide** — a single convention repeats verbatim on every list surface: `<p class="text-sm opacity-70">{message}</p>`, one plain sentence, no action, no icon. Confirmed at `clients/+page.svelte:47`, `clients/[id]/+page.svelte:98` (contracts), `contracts/[contractId]/+page.svelte:199,268,298` (clause notes, rate cards, expenses), `invoices/+page.svelte:75`, `alerts/+page.svelte:29`, and matched in the message catalogue by `dashboard_concentration_empty`, `mail_index_empty`, `mail_contract_templates_empty`, `register_empty`, `import_*_empty` (six more). A related incident, `git` commit `7dded22` ("stop an empty ledger blanking the dashboard", #144): a brand-new, all-zero instance did not get a designed empty state — it got a Svelte hydration crash (duplicate axis-tick keys), fixed by de-duplicating tick values, not by ever building a first-run experience.

## What is wrong

1. **BLOCKER — critical alerts have no path to their subject, though the server already knows it.** Every `AlertDetail` variant except the two system-health ones carries the exact id its subject needs — `workUnitId` (worked_without_approval), `invoiceId` (invoice_overdue), `contractId` (contract_expiring, renewal_window_open, billable_period_closed), `approvalId`+`contractId` (approval_unactioned), `ceilingId` (ceiling_approaching, year_end_overrun_risk), `documentId`+`contractId` (mirror_failure) — `src/lib/server/alerts/types.ts:47-140`. `alerts/+page.svelte:36-38` renders only `alert.title`/`alert.body`, the two strings `alertMessage()` (`render.ts`) produces, and discards every id. A day recorded as worked without approval, named in prose ("Giornata lavorata senza approvazione: Contratto quadro 2026 — piattaforma logistica"), gives the practitioner nothing to click; they must go find the day by hand through Clienti → contract → register. This is the direct opposite of the product's own promise, "no day worked without approval goes unnoticed" — being told without being able to act is not being protected.

2. **BLOCKER — "acknowledge" is the only action, and it is a pure silencer, not a fix.** `acknowledgeAlert` (`state.ts:81-98`) stores a severity-rank floor; the sidebar's unread badge (`+layout.server.ts:17`, `Sidebar.svelte:34-38`) is filtered on `acknowledgedAt === null`, so one click on "Conferma presa visione" drops "Avvisi 2" to "Avvisi 1" with zero change to the underlying ledger. All 11 alert types get the identical verb, whether the alert is a legal-exposure risk (worked_without_approval, invoice_overdue, ceiling_approaching) or an operational FYI (contract_expiring 25 days out) or a system-health warning only the self-hoster can fix (backup_failure). Nothing distinguishes "I will deal with this" from "make the number go away."

3. **MAJOR — no visual weight differentiation beyond a 14px glyph.** `StatusIndicator.svelte` is a well-built component (distinct outline shape per level, colour-blind- and print-safe, label never optional) but the alert _row_ wrapping it is a bare `border p-4` identical for critical and warning — no tinted edge, no background, no ordering signal beyond the sort order. At today's two-alert scale this is invisible; at the scale the product is designed for (11 types × every contract/invoice/day in the ledger) a wall of identical boxes is unscannable, which is the same "chrome deliberately austere" complaint the lead already raised about `Card.svelte`, now applied to the one surface where severity is the entire point.

4. **MAJOR — alert preferences let a single user silently defeat the product's own promises.** `alerts/settings/+page.svelte:92-121` is 22 checkboxes (11 `AlertType`s × digest/push), all defaulting on, all equally easy to switch off, with no distinction between "contract_expiring" (informational) and "worked_without_approval"/"invoice_overdue"/"ceiling_approaching" (the exact three alerts the product's stated promises — "no day unnoticed," "no ceiling crossed blind" — exist to guarantee). Turning one of those off is one unlabelled click, no confirmation, no different visual weight from turning off "mailbox_poll_failure." For a compliance tool this is a self-defeat switch disguised as a preference.

5. **MAJOR — Settings is a stub next to what a self-hoster actually needs, and says so in its own copy.** Fiscal profile is read-only with the UI's own text admitting it: "Configurato direttamente nel database; non esiste ancora un'interfaccia per farlo" (`settings_fiscal_configured_note`). There is no mail-credentials status, no backup status, no ACP runner status, no allowlist view, in the product UI anywhere (confirmed: no route touches those surfaces). This is defensible for a v1 single-operator tool where those stay env-var-configured — but the alert engine already _computes_ backup and mailbox health every run (`fetchLatestBackupRun`, `fetchLatestMailboxPollRun` in `repository.ts`) and the only place that surfaces is a critical alert titled "Backup failing," mixed in among ledger alerts. A self-hoster who wants to check "am I backed up right now" before it becomes a crisis has nowhere to look.

6. **MAJOR — no custom `+error.svelte` anywhere: every 404/400/500 is SvelteKit's bundled, unstyled fallback.** Confirmed by filesystem search (`find src -iname "*error.svelte*"` → nothing) and by `src/hooks.server.ts` (no `handleError`). Concretely reachable, everyday mistake: `invoices/[id]/remind/+page.server.ts:26-27` throws `error(400, m.mail_dunning_not_overdue())` the instant a user opens the reminder flow for an invoice that isn't overdue — one wrong click from the invoice list. There is no nav, no back-to-app link, no brand, in some cases not even the app's own CSS custom properties (the fallback renders outside the root layout). The screenshot sweep didn't catch this because the seed data has exactly one, always-overdue invoice on that path — the code path is real and unguarded on every one of the ~15 `error()` call sites in the app, not just this one.

7. **MINOR — the offline page and the sign-in page do not share a layout, though both are the same "standalone, no-nav page" kind.** Sign-in centers vertically (`min-h-[80svh] flex flex-col justify-center`, `sign-in/+page.svelte:12`); offline does not (`mx-auto max-w-2xl p-8`, `offline/+page.svelte:7`) and sits top-left on a tall viewport (`desktop-it/offline.png`). Both are otherwise good — clear heading, one sentence, one action — and should become the two instances of one shared shell, not two hand-rolled ones.

8. **MINOR — loading/pending feedback exists in exactly one place in this whole area, and it is not the place a slow mobile connection needs it most.** `alerts/settings/+page.svelte:68,78` disables the push subscribe/unsubscribe buttons while `pushSubscriptionStore.busy`. Every other form in scope — `alerts/+page.svelte:49` (acknowledge), `alerts/settings/+page.svelte:91` (save preferences) — uses bare `use:enhance` with no submit callback, meaning no busy state, no disabled-while-pending, nothing to stop a double-submit on a flaky connection (`node_modules/@sveltejs/kit`'s `enhance()` default is a pass-through). Same page, two different standards.

9. **MINOR — empty states are eleven identical grey sentences with the CTA sitting unlinked two lines away.** `clients_empty` ("No clients yet.") renders as plain text while `clients_new_link` ("New client") sits in the page's header-actions snippet, structurally disconnected. On a genuinely empty instance — day one for a new self-hoster — nearly every route renders this same pattern simultaneously: the closest thing the product has to a first-run experience is eleven grey one-liners across eleven pages. The one time this was tested against a truly empty database (commit `7dded22`, #144), the result was a hydration crash, not a designed empty state — proof no deliberate "instance has nothing yet" pass has ever happened.

10. **POLISH — `invoices_empty` = "No unpaid invoices" is a filtered-empty state wearing the generic-empty copy pattern**, the UI-text half of the "paid invoice only reachable by URL" finding already on record for the Invoices area — noted here only because it's the same empty-state component gap: a shared `EmptyState` needs a "no results for this filter" variant distinct from "nothing exists yet," and today's plain-`<p>` convention can't tell them apart.

11. **POLISH — `InstallPrompt.svelte` is the one hardcoded-English surface found in this area.** Every string in it (`"Install mastro for quick access from your home screen."`, `"Install"`, `"Not now"`, the iOS hint sentence) is a literal, not an `m.*` message call — the one violation of "every string is a key in both catalogues" found anywhere in scope. `OfflineDataBanner.svelte` right next to it does this correctly (`m.data_freshness_banner_offline_label`, etc.).

## Options

### Alert row (`/alerts`)

- **A. Restyle in place** — severity-tinted left border/background using the existing `--status-*` tokens (critical = filled edge, warning = hairline), keep the flat list and the single acknowledge button. Effort S. Risk low. Does not fix: no deep link, no differentiated action, still one verb for 11 unrelated situations.
- **B. Restructure the page** — each alert becomes a decision card with a contextual primary action + deep link (see the alert-kind table below), grouped under a heading per severity band with a count ("3 critical"), acknowledge demoted to a small secondary control. Requires extending `alertMessage()`/adding an `alertAction(alert)` function in `render.ts` that returns `{ label, href }` per type, and propagating `clientId` through `ContractDeadlineRow`/`BillablePeriodRow` in `repository.ts` (one extra `select`, `getContract` already returns the column — no schema change). Effort M. Risk medium (touches the alert pipeline, but additively — nothing existing changes shape). Unlocks: alerts becomes a worklist instead of a reading exercise, which is the direct fix for "no day worked without approval goes unnoticed."
- **C. Rethink the flow** — for the five types that represent an unresolved compliance state (worked_without_approval, approval_unactioned, invoice_overdue, ceiling_approaching, year_end_overrun_risk), retire "acknowledge" as a hide-forever action entirely: the alert can only leave the list because the underlying record changed (day gets an approval, invoice gets paid, ceiling drops below threshold). The button that remains _is_ the fix action from option B, with no separate "mute" concept. A "Mute until it changes" control (clearly labelled, not "confirm read") stays available only for the genuinely informational six types (contract_expiring far out, renewal_window_open, billable_period_closed, backup_failure, mirror_failure, mailbox_poll_failure). Effort L — a semantics/policy change, needs the owner's sign-off per type, plus a `state.ts` change to gate which types accept `acknowledgeAlert` at all. Risk highest.
- **Recommendation**: B now — it is the single biggest lever for the product's own core promise and a strict prerequisite for C. Take C to the owner as an explicit policy question ("should acknowledging a worked-without-approval alert ever be possible before the day has an approval?") rather than deciding it here.

### Alert preferences (`/alerts/settings`)

- **A. Restyle in place** — same 22 checkboxes, grouped under headings (Legal exposure / Money / Contracts / System health), "System health" visually set apart as the only genuinely discretionary group. Effort S. Doesn't answer whether the matrix should exist at all.
- **B. Restructure** — default the page to one sentence per band ("Critical alerts always push. Serious alerts always land in the weekly email.") with the full 11×2 matrix collapsed behind "Customize by type." A one-person instance sets this once; the matrix becomes the escape hatch, not the landing state. Effort S–M. Risk low.
- **C. Rethink** — remove the toggle entirely for the five types that guarantee the product's stated promises (worked_without_approval, invoice_overdue, ceiling_approaching, year_end_overrun_risk, approval_unactioned); keep the matrix only for the six discretionary types. Requires gating `setAlertPreference`/`ALERT_TYPES` server-side, plus a "why is this locked" note. Effort M. Risk medium — a product-policy call, same shape as option C above.
- **Recommendation**: B immediately (cheap, matches actual single-user usage). Raise C with the owner alongside the Alerts-row C above — they're the same underlying question ("can this instance turn off its own protection") asked from two screens.

### Settings

- **A. Restyle in place** — same three sections, tidier once the design system exists; add explicit "Not configured in this UI yet — see `.env`" rows (naming the actual env var) for mail, backup, allowlist, runner, so the self-hoster sees the full inventory even where each item still points at docs. Effort S.
- **B. Restructure into an operations panel** — Fiscal profile (status chip: configured/not, still read-only until #146), Mail (configured/not + last successful poll — reusing `fetchLatestMailboxPollRun`, the same query the alert already runs), Backup (last run + status, reusing `fetchLatestBackupRun`), Push (move here from `/alerts/settings` — it's a device setting, not a per-alert-type one), Allowlist (read-only list), Language, Theme (below), Runner (last ACP run timestamp, pending-proposals count). Nothing here needs new backend logic — every data point already exists inside `alerts/repository.ts`, this only reads it a second time from a different page. Effort M. Risk low, purely additive/read-only.
- **Recommendation**: B. Settings should be "am I healthy right now," checkable proactively — today the only way to learn a backup is failing is to be told by an alert titled the same as "a client's contract is expiring."

### Theme control

- **A. Add the switch** — `data-theme` and the full light/dark token set are built, tested (`palette.test.ts`) and already demoed on `/design` (`design/+page.svelte:27-33`, `setTheme`). Add a three-way control (System/Light/Dark) to Settings that sets/clears `document.documentElement.dataset.theme` and persists the choice (`localStorage`, read on `+layout.svelte` mount to avoid a flash). Effort S — the mechanism exists, this is wiring plus two message keys.
- **B/C** — not needed. Automatic OS-driven dark mode already works today via `prefers-color-scheme` (confirmed in `dark-it/*.png` — every screen renders correctly themed); the gap is only the manual override, which is a small, low-risk addition, not a design problem.
- **Recommendation**: A — cheapest item in this whole review relative to what it closes out (a fully-built, fully-tested system with no user-facing switch).

### Sign-in / Offline (standalone-page pattern)

- **A. Unify the shell** — one `StandalonePage` layout primitive (logo, message, primary action, language switch) both routes render into; fixes offline's missing vertical centering as a byproduct. Effort S. Risk none.
- Nothing else warrants a B/C here — the flow itself (single Google button, anti-enumeration rejection copy, retry-and-reload on offline) is already right and should be the reference pattern other standalone screens (this one plus the new error page) copy from, not rebuilt.
- **Recommendation**: A, and explicitly reuse it for the new `+error.svelte` below rather than inventing a third shell.

### Error states (global — no dedicated screen today, a missing pattern)

- **A. Add `src/routes/+error.svelte`** — reuses the `StandalonePage` shell from above: heading built from `page.status`, body from `page.error.message` (every `error(status, message)` call site in the app already passes a translated, on-brand sentence — `m.mail_dunning_not_overdue()`, `m.invoice_not_found()`, etc. — so no new copy is needed for the message itself), one "Back to Today" link. Effort S — one file, no backend change, fixes all ~15+ call sites at once. Risk none, purely additive.
- **B. Copy pass on the thrown messages themselves** — most are already full, on-brand sentences; a few are terse (`document_not_found`: "That document does not exist.") and could name the next step ("go back to the contract"). Effort S, do after A.
- **Recommendation**: A immediately — the single cheapest, highest-leverage fix in this entire review: one file removes the "does not work" experience from every invalid-state path in the product.

### Empty states (global pattern)

- **A. Restyle in place** — keep the one-sentence convention, but attach the CTA that already exists in the page's own header-actions snippet directly under the sentence instead of leaving it structurally separate. Effort S per surface (~12 surfaces, mechanical).
- **B. Shared `EmptyState` component** — icon-free (per the anti-slop guidance): short heading, one sentence, the primary action as a real button (once the design system has one). Two variants: `kind="instance"` (genuinely nothing exists yet — e.g. `clients_empty`) vs `kind="filtered"` (no results for the current view — e.g. `invoices_empty`, which today says "No unpaid invoices" but is styled identically to a truly-empty list). One component, ~12 call sites, new keys in both catalogues (`*_empty_action`). Effort M.
- **Recommendation**: B — cheap, used everywhere, and the direct structural fix for the "blank dashboard" class of defect: a designed, componentized empty state is exactly what stops a degenerate chart or table from ever being the first thing a new instance renders.

### Loading / pending states (global pattern)

- **A. None to restyle** — there is no existing loading treatment outside the one push-button pair.
- **B. A shared pending convention** — either a small `<SubmitButton pending={...}>` wrapping the existing button styles, or a documented `use:enhance` callback pattern (`({ formData }) => { pending = true; return async ({ update }) => { await update(); pending = false; }; }`) applied to every form in scope: acknowledge, save-preferences, and (cross-cutting) every other form in the product. No new dependency — SvelteKit's own `enhance` callback already provides the hook. Effort S to build once, S per form to adopt.
- **Recommendation**: B, listed again under Cross-cutting asks below since it is not specific to this area — every form in every other agent's pages needs the same primitive.

### PWA (install prompt / offline banner / service worker)

- **A. Fix the one real defect: i18n** — extract `InstallPrompt.svelte`'s five hardcoded English strings into `m.*` keys, translate to Italian, matching `OfflineDataBanner.svelte`'s existing correct pattern. Effort S.
- **B. Stacking rule** — both `InstallPrompt` and `OfflineDataBanner` are independently `fixed`/`sticky` and could in principle both be true at once (offline _and_ not-yet-installed); add a shared bottom-stack container so they don't overlap. Effort S.
- **C. None warranted** — the caching architecture (never cache a document, stale-while-revalidate for data, wipe-on-session-invalid, the `redirect: 'manual'` fix from #142) is sound, deliberate, and covered by unit tests (`sw-cache-policy.test.ts`, `freshness-policy.test.ts`, `install-logic.test.ts`). No redesign is warranted.
- **Recommendation**: A + B, both trivial; leave the architecture untouched and call it out to the owner as the one area of this review that's already good.

## Cross-cutting asks

- **`EmptyState` component** — states: `kind: "instance" | "filtered"`, heading, body, optional primary-action button. Needed by every list surface across the whole product (this area's own: alerts; every other area's: clients, contracts, invoices, rate cards, expenses, clause notes, mail templates, register, dashboard concentration, import screens) — roughly a dozen call sites total, so it belongs in the shared component set, not reinvented per area.
- **`StandalonePage` shell** — logo/name, message, one primary action, language switch, vertically centered. Needed by sign-in, offline, and the new `+error.svelte` — three screens, one shell.
- **Severity-treatment tokens for row/card chrome** — today `StatusIndicator` carries shape+colour but nothing propagates that into the container (border tint, background wash) it sits inside. Alerts is the sharpest need, but any future "this row is a warning" surface (ceiling cards, overdue-invoice rows) will want the same left-border/background convention keyed off the same four `StatusLevel`s — define it once as a CSS utility or a `Card` variant, not per-feature.
- **Pending/busy submit primitive** — a `<SubmitButton pending>` or a documented `enhance` callback snippet, applied to every form in the product (this area: acknowledge, save-preferences; every other area has the same gap). One primitive, product-wide adoption.
- **Theme toggle component** — a three-way System/Light/Dark control wrapping the already-built `data-theme` mechanism (`palette.ts`/`palette.css`), for placement in the new Settings operations panel. The token system exists; only the control does not.
- **`+error.svelte`** — one shared root error boundary using `StandalonePage`; every area with an `error(404/400, …)` call site benefits, so it should ship once from wherever the shell primitive lands, not per-route.
- **Button component with a locked/disabled-with-reason state** — needed if the owner approves the Alert-preferences option C (some checkboxes non-optional) or the Alert-row option C (acknowledge disabled until a record changes state) — a disabled control that explains _why_ it's disabled, not just greyed out.
