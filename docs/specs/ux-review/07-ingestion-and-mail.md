# Ingestion and mail

## What is there now

**Proposals list** (`src/routes/proposals/+page.svelte`, screenshots `proposals` desktop-it/mobile-it) is a three-tab queue (In attesa / Accettate / Rifiutate) rendering pending-and-decided proposals as a flat `<ul>` of full-width cards — contract title, a bare confidence percentage, target type + received time, and the excerpt. The code comment at lines 54-58 explicitly documents _why_ it is cards and not a table: a five-column table would force horizontal scroll the moment the excerpt has real text, and the review queue is one of the three phone-critical flows. On mobile the cards work fine as tap targets. The seeded data shows two pending cards from the same contract/timestamp with overlapping excerpts, rendered as two unrelated-looking rows.

**Proposal detail / review screen** (`src/routes/proposals/[id]/+page.svelte`, screenshots `proposal-detail` all four passes) is the human half of "agents propose, humans confirm." A status badge + target type line, a two-line `<dl>` (contract, "Fiducia dichiarata" confidence), then a two-column grid: left is "Estratto di origine" — one italic blockquote line inside a bordered box that is mostly empty at 1440px (screenshot shows roughly 300px of unused height under one sentence); right is "Campi proposti" — three editable inputs (date/text/number, auto-typed by `inputType()`) plus Accept and Reject, both `class="border px-4 py-3.5 text-sm"`, Reject differing only by `opacity-80`. Once decided, the fields panel is replaced by a read-only `<dl>` and a "What changed" section appears below with a link to the resulting day (`resolve('/day/[id]', ...)`) when applicable — that decided view is one of the better-built screens in this area (see "already good" below). The excerpt panel and the `documentId` behind it are never linked to `/documents/[id]`, the download route built for exactly this purpose (`src/routes/documents/[id]/+server.ts`).

**`/import`** (`src/routes/import/+page.svelte`, 565 lines, no `+page.server.ts` by design — the folder walk is client-only) is a six-stage state machine (idle → scanning → analyzing → review → confirming → done, plus error) for bulk-importing exported invoice PDFs/`.p7m`/zips from a folder. Idle state (screenshot `import`, all passes) is a native `showDirectoryPicker()` button plus an unstyled `<input type=file webkitdirectory>` fallback. The review stage (code-only — not screenshotted, since it needs real files picked interactively) is five stacked sections: Recognised (with day-mapping proposals as checkboxes), Already present, Conflicts, To clarify (editable new-client/new-contract forms), and Skipped (with a human-readable reason per row, including `malformed_document` with the parser's own message). The done stage reports created/failed counts including a per-item failure list. Server-side, `/import/analyze` is read-only (parses, matches, never writes) and `/import/confirm` is the only write path, gated on explicit user selection.

**`/mail`** (`src/routes/mail/+page.svelte`) is a flat table of contracts with mail activity configured, one "Apri" link per row — no poll history, no per-contract last-synced state, no unread/new-message count. **`/mail/contracts/[id]`** (screenshot `mail-contract`) stacks three independent settings forms (auto-send toggle, template language, IMAP inbound folder) each with its own Salva button, then a templates table (name/trigger/attachments/edit+send links) below the fold, with "Registro giornate" (day register) reachable only via a small text link in the page actions slot. **The day register** (`.../register`, screenshot `mail-register`) is a from/to date-range form defaulting to the calendar month, PDF/CSV download links, and a table of billed days with a channel+sender "Approvazione" column and a totals row — the seeded pass shows it empty ("Nessuna giornata fatturata in questo periodo") because the hardcoded current-month default doesn't hit the seeded data's actual billed period.

**Template new/edit** (`TemplateForm.svelte`, shared by `.../templates/new` and `.../templates/[templateId]/edit`, screenshots `mail-template-new`/`-edit`) is name/subject/body (plain `<textarea rows=6>`), a one-line plain-text hint listing available `{{placeholder}}` tokens below the body, an attachment-kind checkbox pair (day register PDF/CSV), and a trigger radio group (manual / on issue / N days before due / N days after due). Validation happens server-side in `email-template-form.ts`, which rejects any `{{unknown}}` token at save time via `findUnknownPlaceholders` — a genuinely good "fail early, not at send time" design. **Template send** (`.../templates/[templateId]/send`, screenshot `mail-template-send`) is a two-step form: fill period + invoice number/amount/due date + recipients → Preview (renders the real subject/body/attachment list server-side against the template's own language) → a second, separate form with hidden fields that actually dispatches. The invoice figures are hand-typed every time; the on-screen hint says why ("si inseriscono a mano finché non esiste la tabella invoice di #26").

## What is wrong

1. **BLOCKER — the proposal's source document is unreachable.** `src/routes/proposals/[id]/+page.server.ts:54-71` loads the proposal but never passes `row.documentId` to the client, and `+page.svelte` never renders a link to it. `/documents/[id]` (`src/routes/documents/[id]/+server.ts`) exists, is session-gated, and its own doc comment says the point is that "the source document is what counts when a client disputes a day" — but nothing in the app links to it (`grep` for any `resolve('/documents...')` call anywhere in `src/routes` returns zero hits). The review screen asks a human to confirm a day off one italic sentence with no way to open the email or PDF that sentence was extracted from. This is the single most direct violation of invariant 4 in the whole surface, on the one screen where it matters most.
2. **BLOCKER — the send screen requires hand-typing real financial figures for a real client email, and the on-screen excuse for that is stale.** `.../send/+page.svelte:74-100`, backed by `mail-send-form.ts:27-34`. The visible hint (`messages/en.json:609`, `mail_send_form_hint`) tells the operator invoice number/amount/due date are typed by hand "until #26's invoice table exists to read them from" — but `src/lib/server/repositories/invoice.ts` (createInvoice, getInvoiceWithLines, `listUnpaidInvoices`) shows #26 has already shipped. The UI was never wired to it. Every registry/dunning email that goes out is one transcription slip from quoting the wrong amount or due date to a client, with zero cross-check against the ledger — the exact class of silent, unnoticed error the product exists to prevent, pointed outward at a client relationship instead of at a day.
3. **BLOCKER — `/proposals` is not in any persistent navigation.** `src/lib/nav/items.ts:19-47` (`NAV_GROUPS`, `BOTTOM_BAR_HREFS`) has no Proposals entry in the sidebar, the bottom bar, or the mobile "More" sheet. The only entry point is the dashboard home CTA (`src/routes/+page.svelte:35-42`) with a pending-count badge — genuinely useful, but it means leaving the dashboard (to open a client, a contract, a day) severs the path back to the review queue; you must return home first. For a screen that exists so "no day worked without approval goes unnoticed," making it reachable from exactly one page in the app is a real gap, only partly offset by the badge.
4. **MAJOR — two proposals from one email present as two unrelated cards, and their excerpts overlap without warning.** `proposals/+page.svelte:59-89` is a flat list with no grouping by source document/thread. Screenshot `proposals`: both pending cards read "Contratto quadro 2026 — piattaforma logistica · 13 ago 2026, 16:20" (same contract, same minute) — a dead giveaway they came from the same email — yet nothing ties them together, and their excerpts partially overlap ("18 agosto, la seconda mezza" at 72% vs "ti confermo le giornate del 17 e 18 agosto" at 90%). A reviewer working the queue top-to-bottom has no way to notice these might both be proposing the 18th.
5. **MAJOR — Accept and Reject are visually identical.** `proposals/[id]/+page.svelte:78-88`: both buttons share `class="border px-4 py-3.5 text-sm"`; Reject only adds `opacity-80`. No color or spatial differentiation separates "write this to the ledger" from "discard it" — on the mobile layout (screenshot `proposal-detail` mobile-it) they sit 12px apart with equal width. This is the same "primary action has no visual language" defect the lead flagged chrome-wide, but here it sits on an actual branch point with consequences, not just inconsistent styling.
6. **MAJOR — evidence panel is nearly empty, fields panel is dense; attention goes the wrong way.** `proposals/[id]/+page.svelte:39-44`: the "Estratto di origine" box is a fixed grid cell holding one sentence, ~300px of unused height on desktop (screenshot `proposal-detail`). The eye lands on the visually heavier "Campi proposti" box, backwards for a screen whose entire job is "check the fields against the evidence."
7. **MAJOR — confidence is a bare, uncalibrated number.** `formatPercent` (`src/lib/i18n/format.ts:75-77`) renders "72%"/"90%" identically — no color, no threshold, no comparison to what's normal. Nothing distinguishes "worth a second look" from "routine" at a glance, on the one figure this screen most needs to be legible fast.
8. **MAJOR — no visibility into whether mail ingestion is even running, anywhere in `/mail`.** `mail/+page.svelte` and `.../contracts/[id]/+page.svelte` never read `mailbox_poll_run` (`src/lib/server/repositories/mailbox-poll-run.ts`), even though `detectMailboxPollFailure` (`src/lib/server/alerts/detectors.ts:549-586`) already fires "serious" after 3 stale hours and "critical" on outright failure or a poll that has never run. Between a healthy poll and that 3-hour mark there is no "last checked 6 minutes ago" anywhere near the "Posta in arrivo" folder field (`.../contracts/[id]/+page.svelte:88-106`) that this same setting feeds. The operator only learns the proposal pipeline stalled once Alerts already calls it critical.
9. **MAJOR — the template editor doesn't tell you all the placeholders that exist.** `TemplateForm.svelte:40-45` is a plain `<textarea>`; the only help is one line of prose (`mail_template_form_body_hint`) listing six tokens — `invoice_number, period, amount, due_date, day_list, day_total` — but the schema defines seven (`src/lib/server/db/schema/email-template.ts:17-25` includes `days_late`). `days_late` is exactly the token a dunning template (the `days_after_due` trigger) needs most, and it's invisible on the one screen where you'd reach for it.
10. **MAJOR — ingestion/settings tables use the exact pattern this codebase already rejected.** `mail/+page.svelte:16-37`, `.../contracts/[id]/+page.svelte:121-155`, `.../register/+page.svelte:49-74`, and `import/+page.svelte:321-350,360-384,490-505` all render plain semantic `<table>`s — the shape `proposals/+page.svelte:54-58`'s own comment names as the reason proposals was rebuilt as cards ("a five-column table is exactly the shape that forces horizontal scrolling once [a] column has real text in it"). `RecordList.svelte` already exists and solves this with a CSS-only table/card breakpoint, but none of these screens use it. The register's "Approvazione" column (channel + sender) is a prime candidate to overflow, and every pass measured it with **zero rows** (report.json), so the screenshot sweep never actually exercised it with real data.
11. **MINOR — mobile mail-contract page buries the templates table under three stacked settings forms.** Screenshot `mail-contract` mobile-it: auto-send toggle, template language, inbound folder — each its own bordered card with its own Salva button — all sit above "Modelli," even though the templates table (edit/send links) is the thing actually opened often; the settings are opened rarely.
12. **MINOR — the day register's default date range doesn't reflect the contract's own billing period.** `register/+page.server.ts:8-13` hardcodes "current calendar month" regardless of the contract's invoicing cadence (monthly/quarterly/annual/on-completion) or what's actually unbilled — the seeded pass renders empty (screenshot `mail-register`, "Nessuna giornata fatturata in questo periodo") because the real unbilled period doesn't happen to be this month.
13. **MINOR — recipients on the send screen are a raw comma/newline textarea.** `.../send/+page.svelte:103-107`: no per-address chips, no inline validation until the full form round-trips server-side (`EMAIL_PATTERN` check in `mail-send-form.ts:70-71`). Workable, but the one field that decides who receives real client figures deserves better than a blind `<textarea>`.
14. **POLISH — every proposal detail page has the identical heading "Rivedi proposta."** No contract, date, or target-type differentiator in the `<h1>` itself (only below it) — with several open proposals, browser tabs/history are indistinguishable.
15. **POLISH — the import review screen's top summary strip (Recognised/Already present/Conflicts/To clarify counts, lines 239-251) isn't clickable.** On a large batch, the counts that matter (conflicts, to-clarify) are visible up top but not anchored to their section — still a full scroll past everything else to reach them.

## Options

### Proposal review screen (`/proposals/[id]`)

- **A. Restyle in place (keeps the side-by-side evidence/fields layout).** Fix the emptiness and the missing source without changing the IA: shrink the evidence card to fit its content (no fixed-height grid cell — `align-self: start`), add sender/received-at/thread metadata above the excerpt, add a visible "Open source document" link to `/documents/[id]` (which requires passing `documentId` through `+page.server.ts`'s load), replace the bare percentage with a small confidence chip (color/label tier: e.g. "High confidence" / "Review carefully"), and differentiate Accept (primary, filled) from Reject (secondary/outline, not just dimmed). Effort **S**. Risk: low — no data model or route changes, only load-function and markup edits. Does not fix: the "no sense of a queue" problem (#4) or the flat-list grouping — a reviewer still opens one proposal in isolation.
- **B. Restructure the page — evidence-first, single column, queue-aware.** Drop the two-column grid. Lead with the full evidence (excerpt, highlighted against the full message via a "view full message" expandable pulled from the source document, not just one blockquote line), then the proposed fields as an edit-in-place table below it, with Accept/Reject anchored at the bottom as a sticky action bar (useful on mobile too, where the two-column layout already collapses to one column). Add a "1 of 2 from this email" strip at the top when the proposal's document has sibling proposals (`listProposalsForDocument`), with quick prev/next inside the same detail page so a reviewer can process a multi-proposal email without returning to the list each time. Effort **M**. Risk: medium — touches the load function (needs sibling proposals + document metadata) and the primary layout; existing tests for the accept/reject actions are unaffected since they're server actions, not layout. Unlocks: the grouping requirement from the assignment (see next section) at the detail-page level, and a much stronger "check evidence, then fields" reading order.
- **C. Rethink the flow — inline review inside the queue, no detail page for the common case.** For the common case (one proposal, high confidence, simple fields), let the list itself expand a proposal card into an inline accept/reject panel (excerpt + fields + actions) without navigating away — closer to a true "swipe through the queue" review, matching the 30-second promise. Keep `/proposals/[id]` as the deep-linkable, full-detail view for anything low-confidence, multi-field, or opened from an alert/link elsewhere. Effort **L**. Risk: higher — two UIs to keep in sync (inline panel vs. detail page), more state management in the list page, and it changes how accept/reject actions are wired (progressive enhancement inside a list vs. a dedicated route's form actions). Only worth it once the queue is used often enough that per-item navigation is itself the bottleneck.
- **Recommendation**: **B**. It directly fixes the emptiness/source problems in place (#1, #5, #6) while adding the queue-awareness the assignment specifically asks for, at a cost the team can absorb in one pass; **C** is a bigger bet that should wait until real usage data says single-proposal review time is the bottleneck, not the missing source link.

### Proposals list (`/proposals`) — multi-proposal grouping

- **A. Restyle in place.** Add a lightweight visual join: proposals sharing `documentId` render as one bordered group with a "2 proposals · same message" label above the cards, keeping today's card markup inside. Effort **S**. Risk: low. Does not fix: still requires opening each card individually to act on it.
- **B. Restructure — thread-grouped queue.** Query `listProposals` grouped by `documentId` server-side; render one thread header per source email/document (sender, subject if available, received-at) with its child proposals nested underneath, each with its own confidence + excerpt but a shared "Accept all" / "review individually" affordance at the thread level (accepting each one is still a separate transaction — no bulk-write bypass of `acceptProposal`, just a UI convenience that fires the same per-item action for each). Effort **M**. Risk: medium — changes the list query and the card markup; must preserve the existing pending/accepted/rejected tab filter per proposal, not per thread (a thread can straddle two states). Unlocks: exactly the "what a review queue should look like when one email produces several proposals" ask, and gives the accepted/rejected history tabs the same grouping so "what did this email turn into" reads as one unit afterward.
- **Recommendation**: **B**, scoped to grouping by `documentId` only (no new schema) — it is the direct answer to the assignment's explicit ask and reuses data already on the `proposal` row.

### `/import`

- **A. Restyle in place.** Style the native folder-picker button and file input as first-class controls (dropzone look, drag-and-drop where the File System Access API is available), make the top summary counts (#15) anchor-link to their section, and give the five review sections a shared card treatment instead of ad hoc borders. Effort **S**. Risk: low — the state machine and server contract are untouched. Does not fix: the flow is still five long sections regardless of how much needs a decision.
- **B. Restructure — triage-first review.** Reorder the review stage so only sections needing a decision (Conflicts, To clarify) are open by default, with Recognised and Already-present collapsed behind their counts (still fully visible on expand, nothing hidden from the confirm step); Skipped stays visible but de-emphasized since it needs no action. Effort **M**. Risk: low-medium — purely a client-side reorder/collapse of sections already rendered from the same `ReviewResult`, no server changes. Unlocks: a large batch (the realistic case for a folder of exported invoices) becomes scannable in seconds instead of a full-page scroll.
- **Recommendation**: **B** — cheap relative to its payoff, and it's the direct answer to "judge the flow end to end… what a partial import looks like." Keep **A**'s dropzone polish as a fast-follow, not a blocker.

### Mail index + per-contract page (poll visibility)

- **A. Restyle in place.** Add a one-line status strip to `/mail`'s contract table (a column: "Last synced 4m ago" / "Never" / "Failed") and to `.../contracts/[id]` next to the inbound-folder field, reading `getLatestMailboxPollRun` — reusing the exact detection window `detectMailboxPollFailure` already defines (fresh/stale/failed) so the two surfaces never disagree. Effort **S**. Risk: low — read-only addition, one new query per page. Does not fix: there's still no way to trigger a poll on demand from the UI (if that's desired — the codebase notes polling is cron-driven, not user-triggered, which is a legitimate operational choice, not a UI gap).
- **B. Restructure — a per-contract "inbox" view.** Replace the settings-first `.../contracts/[id]` layout with a two-part page: an activity panel up top (poll status, archived-thread count, link to any proposals still pending from this contract's mail) and the settings (auto-send, template language, folder) moved into a collapsed "Settings" section below, since they're rarely touched. Effort **M**. Risk: medium — bigger layout change, needs `listInboundThreadsAwaitingExtraction` and proposal counts scoped by contract (not currently exposed that way — `listProposals` filters by status only, not contract). Unlocks: the per-contract page finally answers "is this client's channel working and current," not just "what are the settings."
- **Recommendation**: **A** now — it's the one addition most directly requested (poll runs) at very low cost; **B** is worth doing once (if) contract-scoped proposal counts already exist for other reasons, so it isn't built solely for this.

### Template editor (new/edit)

- **A. Restyle in place.** Fix the placeholder hint to list all seven tokens including `days_late` (a one-line message-catalogue fix), and turn the hint into clickable chips that insert `{{token}}` at the cursor instead of prose the author has to retype correctly. Effort **S**. Risk: low. Does not fix: there is still no way to see what the email will actually look like while writing it — only after saving, on the separate Send screen.
- **B. Restructure — live preview pane.** Add a read-only preview pane beside (desktop) or below (mobile) the subject/body fields that re-renders on input using placeholder-name echoes (`{{amount}}` shown literally, since real figures don't exist until Send) — catches unbalanced `{{}}` and unknown tokens before submit, not just after. Effort **M**. Risk: low-medium — client-side only, `findUnknownPlaceholders` can run in the browser since it has no server dependency (pure regex over the schema constant). Unlocks: template authoring stops being "save, then find out."
- **Recommendation**: **A** first (it's a strict, cheap improvement with a real, cited defect — the missing `days_late` token); **B** as a near-term follow-up once the chip-insert control from **A** exists, since it's a natural extension of the same input.

### Template send screen

- **A. Restyle in place.** Keep the manual invoice-number/amount/due-date fields but make the risk visible: show the matching invoice from `listUnpaidInvoices`/`getInvoiceWithLines` (by contract) as a read-only reference card next to the form ("Compare against: INV-2026-014, €1,800.00, due 2026-08-25") so a mismatch is visually obvious before Preview, without yet requiring a schema/flow change. Effort **S**. Risk: low. Does not fix: the figures are still typed, not sourced — the reference card can drift out of sync with what gets typed if the operator doesn't look.
- **B. Restructure — select an invoice, don't retype it.** Replace the three manual fields with an invoice picker (dropdown or small list) scoped to the contract, sourced from the already-shipped `invoice` repository; number/amount/due-date become derived, read-only display, not input. `parseMailSendForm` changes from parsing three raw strings to resolving one `invoiceId`. Effort **M**. Risk: medium — real behavior change to a repository and its tests (`mail-send-form.ts`, its test suite, and the two `+page.server.ts` actions), but it removes an entire class of hand-entry error and the stale on-screen hint becomes simply untrue-and-removable. This is the one place in this document where "effort" undersells the value: it's a small, mechanical change with an outsized correctness payoff.
- **Recommendation**: **B**. The manual-entry justification in the code and copy is already obsolete (the invoice table it was waiting on has shipped); shipping **A** alone would mean deliberately choosing to keep a known-fixable, real-money defect for another cycle.

### Ingestion destinations — three surfaces or one?

- **A. Keep three, but cross-link them.** `/proposals` (day proposals from mail), `/import` (bulk invoice files), `/mail` (compose/settings) stay separate routes — they genuinely do different things structurally (different data models: `proposal` vs. the import pipeline's client-side `ReviewResult` vs. `email_template`/send). Add: a "pending proposals for this contract" count on `.../mail/contracts/[id]` (so the settings page that configures a mailbox links forward to what it produces), and a persistent nav entry for Proposals (fixes finding #3 regardless of which option is chosen here). Effort **S**. Risk: low — no data-model change, only added links/queries. Tradeoff: the three destinations remain conceptually disjoint from a new user's perspective — nothing on `/import`'s invoice flow ever says "by the way, day proposals come from a different email-driven pipeline, over there" — so discoverability stays weak even after cross-linking.
- **B. Consolidate into one "Inbox" surface with two lanes.** A single `/inbox` (or repurposed `/mail` as the umbrella) with two tabs: "Proposals to review" (today's `/proposals`, grouped by source email per the option above) and "Invoices to import" (today's `/import` review stage, unchanged internally) — plus a settings/compose area demoted to a secondary "Templates & mailboxes" tab within the same shell. This does not merge the underlying data models or server logic — `proposal` rows and the import pipeline's `ReviewResult` stay exactly as different as they are today — it only unifies where a human goes to find "things an agent produced that need a decision." Effort **M**. Risk: medium — mostly routing/IA (new top-level route, redirects from the old three, nav updates), plus real design work to make two structurally different review UIs (proposal cards vs. import's five sections) feel like one product instead of two screens wearing the same wrapper. Tradeoff: `/mail`'s compose/settings role (which is not a "review a proposal" task at all — it's configuration and outbound sending) gets awkward inside an "inbox" framing; it may deserve to stay a genuinely separate destination even under this option.
- **Recommendation**: **A** now, with the specific nav fix (Proposals in persistent chrome) and the specific cross-link (contract → its pending proposals) called out above as concrete, low-risk deliverables; treat **B** as a deliberate follow-up decision for the product owner, not a default, because the two review flows (proposal accept/reject vs. import confirm) really do have different shapes and forcing one IA around them risks the "same wrapper, different product" trap without a genuine UI unification pass to back it up. The daily rhythm the product actually needs — email arrives → proposal appears → human accepts → day exists — is served today almost entirely by `/proposals` plus the dashboard CTA; that loop should be tightened (Option B design above, plus the nav fix) before deciding whether it's worth merging with the structurally different bulk-import and compose destinations.

## Cross-cutting asks

- **Button component** with primary / secondary(outline) / destructive / disabled / loading states. Needed by: proposal detail (Accept = primary, Reject = destructive-secondary, not `opacity-80`), import (Confirm), mail send (Preview, Send), template forms (Save/Create), mail-contract settings forms (three separate Salva buttons today, all identical).
- **Confidence/score indicator** (chip or small meter, with a defined threshold for "needs a closer look") — needed by proposal list and detail; the raw `formatPercent` output should never be the only signal again.
- **Evidence/source-document link pattern** — a small, reusable "Open source (PDF/email)" affordance wired to `/documents/[id]`. Needed here (proposal detail) and flagged for whoever owns day detail / expense / invoice screens, since the same `document` table backs approvals and receipts there too — this should not be invented three separate times.
- **Inline notification / success banner** — today `mail_send_success` and the import "done" summary each hand-roll their own `<p class="border border-current p-3">`. One component (success/warning/error variants) covers both plus template-save confirmation.
- **Adopt `RecordList.svelte` everywhere a `<table>` currently appears in this area** (mail index, templates table, register table, import's three summary tables) instead of building a new component — it already exists and already does the table→card breakpoint the proposals list had to hand-roll a whole different markup shape to get.
- **Grouped-list / thread wrapper** (header + nested items, used for "N proposals from one email") — likely reusable wherever alerts or other producer-generated items eventually need the same "these came from one source" framing.
- **"Last synced" status strip** (label + relative time + ok/stale/failed tone) for the mailbox poll status — worth pooling with whatever the dashboard/alerts area builds for `backup_run`/`document_mirror_run`, since all three follow the identical run-record shape and the identical "silence itself becomes the alert" logic.
- **Placeholder-token input** (chip list that inserts `{{token}}` into a focused text field) for the template subject/body editor — narrow, single-purpose, but only worth building once.
