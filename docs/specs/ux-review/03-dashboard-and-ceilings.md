# Dashboard and ceiling/forecast presentation

## What is there now

**Home screen shell** — `src/routes/+page.svelte` + `+page.server.ts`. `Page` renders `title="mastro"` with `subtitle={m.landing_tagline()}` ("A ledger for days that must be approved before they are worked.") as the page's own `h1`/subhead (`+page.svelte:32`; confirmed by `report.json`, every one of the four passes records `h1: "mastro"` for the `dashboard` route). Below that: two CTAs (`Record a day`, filled black; `Review proposals`, outlined, with a pending-count badge), a "Press N" shortcut hint, an inline "Calendar" text link, then three `<section class="widget">` blocks — Ceiling, Cash calendar, Client concentration — and a footer with the signed-in email and a second sign-out button. Screenshots: `dashboard` in all four passes (`desktop-it`, `desktop-en`, `mobile-it`, `dark-it`).

**Ceiling widget** — `src/lib/dashboard/CeilingMeter.svelte`, one card per active whole-practice ("pack-origin") ceiling, fed by `src/lib/server/fiscal/ceiling-status.ts`'s `evaluateActiveCeilings` and `src/lib/server/fiscal/forecast.ts`'s `forecastRevenue`, assembled in `+page.server.ts:100-145`. Each card: a label, a big bold current-value figure with "of €limit", a horizontal progress track with unlabelled tick marks (threshold/limit/projection, all `title`-only), a `StatusIndicator` + basis sentence, and a muted projection sentence. The seeded instance is on Italy's flat-rate regime (`src/lib/server/fiscal/packs/it-flat-rate.ts`), which legally carries two figures against the _same_ cash-received number: an 85 000 € soft ceiling (lose the regime next year) and a 100 000 € hard ceiling (lose it immediately, VAT due). Screenshot: `dashboard` — both cards read "€3,150.00" as the headline.

**Cash calendar** — `src/lib/dashboard/CashCalendarChart.svelte`, a 12-month stacked bar chart (collected/committed/projected, one hue light-to-dark) over a rolling ±6-month window (`forecastRevenueByMonth`, `+page.server.ts:23-24,88`), with vertical marker lines for contract expiry/renewal-notice/irrevocability dates. Desktop renders a native-sized SVG inside `ChartFrame` (chart/table toggle); below 640px a hand-built vertical list (`.calendar-phone`) replaces it entirely, one card per month with an inline mini-bar and any marker/assumption text appended as prose. Screenshots: `dashboard` desktop passes (SVG) and `mobile-it` (phone list).

**Client concentration** — `src/lib/dashboard/ConcentrationChart.svelte`, a horizontal bar per client (share of this year's revenue, `fetchClientRevenueBreakdown`) with a dashed reference line per active `percentage_share` ceiling (pack- or contract-origin). Seeded data has one client at 100% of revenue against a 35% contract cap — one full-width bar, one reference line near its start, one text paragraph below repeating the cap. Screenshot: `dashboard`, all passes.

**Shared chart chrome** — `src/lib/design/charts/{ChartFrame,Axis,Grid,Legend,DataTable,StatusIndicator}.svelte`. `ChartFrame` always renders a table twin and defaults to it under 640px (`ChartFrame.svelte:35-52`); `Axis` draws one hairline tick + label per entry with no collision handling (`Axis.svelte:32-56`); `StatusIndicator` is the one piece of the system that already does status right — shape + glyph + label, colour never alone (`StatusIndicator.svelte:14-18`). `src/routes/design/+page.svelte` documents the palette (categorical/sequential/certainty/status) and a validator report but nothing about composing these primitives into a _page_.

## What is wrong

1. **BLOCKER — the home screen contains zero days.** The product's own domain is a per-day approval ledger; the first screenful is the app's name, a tagline, two forecasting widgets and a chart, and not one work unit, proposal detail, or "what happened today" fact. `+page.server.ts` never queries `work_unit` at all — only ceilings, forecast, contracts, clients, and the _count_ of pending proposals. Evidence: `+page.svelte:32-88`, `+page.server.ts:78-98`, screenshot `dashboard` (all passes). This is the gap between what the owner asked for ("registro delle giornate") and what he is shown (a mini BI dashboard).

2. **BLOCKER — "no day worked without approval goes unnoticed" is not served by the home screen.** A ready-made query already exists for exactly this (`fetchWorkedWithoutApprovalRows` in `src/lib/server/repositories/work-unit.ts` / the alert detector `detectWorkedWithoutApproval`, always `critical`), but the dashboard load function never calls it, and nothing about a WWA day appears anywhere on `/`. The only place it can surface is `/alerts`, which per the lead's finding #6 is not actionable (no link back to the day) and dismissible with one click. A day silently sitting in `worked_without_approval` is invisible unless the owner separately visits Alerts and doesn't dismiss it. This directly contradicts the stated product promise.

3. **MAJOR — the two ceiling cards read as duplicates of each other.** Both show the identical headline "€3,150.00" because both track the same cash-received-this-year figure against two different limits (85 000 soft / 100 000 hard — `it-flat-rate.ts:6-9,27-34`). Nothing in the layout says "this is the same money against two different, differently-severe consequences" — they sit as two visually identical sibling cards in a `grid-template-columns: repeat(auto-fit, minmax(16rem,1fr))` (`+page.svelte:135-139`), same size, same green tick, same layout. A user skimming for ten seconds reads "two ceilings, both fine" and never learns that one of them, if crossed, is a same-year event with VAT consequences and the other is a next-year regime loss. Evidence: `+page.server.ts:108-111` (`heroCeilings` filter keeps both), screenshots `dashboard` (desktop-it/en/dark).

4. **MAJOR — the ceiling meter's headline number never changes with severity.** `.figure` (`CeilingMeter.svelte:123-129`) is hard-set to `color: var(--text-primary)` regardless of `status.level`; only the thin fill bar and the small `StatusIndicator` two rows below carry colour. The one number the eye actually lands on first (36–40px, bold) looks identical whether the ceiling is untouched or already crossed. "No ceiling crossed blind" needs the opposite: the biggest, boldest thing on the card should be the thing that changes.

5. **MAJOR — the track's tick marks are unlabelled to the eye.** The threshold, limit and projection ticks (`CeilingMeter.svelte:56-72`) carry their meaning only in an HTML `title` (desktop hover) and a visually-hidden `<span class="sr-only">`. On the phone this product is meant to be run from, there is no hover; the marks are three unexplained vertical lines on a bar. A first-time reader cannot tell the dashed line from the solid one, or what either means, without a mouse.

6. **MAJOR — the projection note never escalates.** `.projection-note` (`CeilingMeter.svelte:193-197`) is always `var(--text-muted)` at `0.75rem`, whether the projected year-end figure is 8% of the ceiling (seeded case) or 190% of it. The one sentence in the card that says "here is where this is headed" looks like a footnote in every case, including the one — a projected breach — the task specifically calls out as needing to read clearly.

7. **MAJOR — two incompatible visual languages for "ceiling."** The pack-origin whole-practice ceilings render as `CeilingMeter` progress bars in the "Soglia/Ceiling" section; a contract's client-share cap renders as a dashed reference line crossing a bar in the concentration chart, with its own text paragraph. Both are "a limit that must not be crossed" (AGENTS.md invariant 2), but a user has to learn two different reading conventions on the same page to catch either kind.

8. **MAJOR — cash calendar's month axis is unreadable.** `formatMonthShort` already tries to shorten the label (`src/lib/i18n/format.ts:119-127`, its own comment admits "twelve `formatMonth`-length labels in a row would overlap") but still emits `"feb 2026"`-style strings into a 44px pitch (`barWidth 28 + barGap 16`, `CashCalendarChart.svelte:42-43,341-345`), and `Axis.svelte` has no collision or rotation logic at all — it just draws every label, always. The result, visible in every desktop/dark screenshot, is a single unreadable run: `feb 2026mar 2026apr2026mag2026giu2026lug2026ago2026set2026 ott 2026nov2026dic2026gen 2027`. The page itself is `width="wide"` (72rem available, `Page.svelte:23,40`) while the SVG is pinned to a 616px native width (`plotWidth = 12 × 44 − 16`) — the chart is using a fraction of the room the page already has.

9. **MAJOR — non-round y-axis ticks.** `cashCalendarYTicks` (`cash-calendar.ts:87-91`) takes `top = round(yMax)` with `yMax = max(monthTotal) × 1.1`, then ticks at `[0, round(top/2), top]` — whatever that arithmetic lands on, rounded to the minor unit, never to a human step (10/25/50/100/…). Screenshot shows `5985,00 €` / `3492,50 €` / `0,00 €`: three numbers nobody can hold in their head, on a chart whose entire job is "can I read the shape of my cash at a glance."

10. **MAJOR — contract-date marker lines have no visible label.** The vertical lines in the cash calendar (expiry/renewal-notice/irrevocability) are distinguished only by dash pattern (`markerDashArray`, `CashCalendarChart.svelte:93-97`) and explained only by one generic paragraph below the chart ("solid for an expiry, dashed for…", `m.dashboard_cash_calendar_marker_key`) plus a hover/focus tooltip for _which_ contract. On the phone list, where there is no hover, the same information becomes a full prose sentence appended under every affected month (`row.markers`, joined with `'; '` when more than one marker falls in a month) — e.g. the `settembre 2026` row in the `mobile-it` screenshot carries two full sentences of legalese-adjacent text ("Termina la finestra di irrevocabilità per Assicurazione continuativa dallo studio Bertani & Partners; Termina la finestra di irrevocabilità per Contratto quadro 2026 — piattaforma logistica S.p.A.") wrapping to three lines under a single €0,00 bar. This is the "wall of per-row annotations" the brief names, and it is worse than the desktop version because the desktop tooltip is at least optional.

11. **MINOR — concentration chart's reference line is unlabelled on the line itself.** Same pattern as #10: the dashed cap line (`ConcentrationChart.svelte:108-117`) carries no `title`/`aria-label`, its meaning arrives only via the `.reference-note` paragraph beneath the whole chart (`ConcentrationChart.svelte:152-158`). With one client at 100% share, the bar fills the entire plot width and the 35% line sits inside it with nothing pointing at what it is until the reader's eye drops below the SVG.

12. **MINOR — the chart/table toggle is per-instance and doesn't remember a choice across widgets.** `ChartFrame`'s `view` state (`ChartFrame.svelte:36-52`) is local to each chart; picking "Table" for the cash calendar has no effect on the concentration chart two sections down. Two independent controls doing the same job, both visible on one screenful, reads as inconsistency rather than flexibility.

13. **MINOR — duplicated account chrome.** `Sidebar.svelte:45-51` already renders the signed-in email, language switch and a sign-out button in the persistent nav; `+page.svelte:82-87` renders a second, near-identical block (email line + sign-out button) at the foot of the dashboard's own content, visible on every desktop/dark screenshot directly below the concentration card. It is the _only_ account/sign-out affordance on mobile (no sidebar there), so it cannot simply be deleted — but on every viewport where the sidebar is present it is dead duplicate chrome competing with the actual content for the last screenful.

14. **MINOR — redundant calendar link.** `Calendario`/`Calendar` appears twice in the first screenful reachable state: once as a persistent sidebar nav item, once as an inline underlined text link directly under the CTA row (`+page.svelte:46`). Not harmful, but it's one more inconsistent-looking affordance (link style is different again from both CTA buttons) on a page that already has too many competing button styles.

15. **MINOR — "Press N" hint on a page that promises to work from a phone.** `+page.svelte:44`/`home_record_day_shortcut_hint` renders unconditionally, including in the `mobile-it` screenshot at 390px, where there is no physical keyboard for the shortcut to apply to. Same defect the lead flagged project-wide (finding #9), concretely present here.

16. **POLISH — dashboard has no distinct desktop layout despite `width="wide"`.** The page opts into the 72rem container (`Page.svelte:39-41`) presumably for the charts, yet every section still stacks in a single column exactly as a `width="text"` page would; the extra width buys the SVGs a wider canvas but nothing about the page's information architecture uses it (no side-by-side ceiling + calendar, no summary rail). The width choice is spent on chart padding, not on structure.

## Options

### Dashboard (home screen)

Three genuinely different concepts, because "restyle the same three widgets" cannot fix finding #1 and #2 — the composition itself is wrong, not just its styling.

**Concept 1 — Attention queue.** The home screen's job is triage: what needs a decision from me right now. Above the fold: a single ordered list — pending proposals to accept/reject, days in `worked_without_approval` (with a direct link to approve), invoices overdue or due within N days, active critical alerts — each row one line, a status glyph, and a link straight to the record. Ceilings/forecast/concentration collapse to a compact strip below, glanceable but secondary. This reads the product as "a todo list with financial guardrails," matches "30 seconds a day" directly (the queue _is_ the 30-second task), and makes #2 structurally impossible to fail (a WWA day has nowhere else to hide).

**Concept 2 — Period ledger.** The home screen's job is "show me my current period" — this month's or this billing period's days, one row each, state visible (proposed/approved/worked/invoiced/paid/…), with the ceiling and cash-forecast widgets demoted to a sidebar or a second tab. This reads the product as a ledger first, a forecasting tool second — closest to the literal meaning of "registro" the owner used. Strongest on "this year's history is loaded" (the days are right there, scrollable); weakest on triage (a stale WWA day is just one more row unless specifically flagged).

**Concept 3 — Money-and-risk cockpit.** Keep the current widget set but reorganise and fix it: a top strip of small stat tiles (this year's collected/committed/projected, days pending, WWA count — all one glance, no charts), then the ceiling meters redesigned to read severity at a glance (see below), then the cash calendar and concentration charts fixed as dataviz. This is the least disruptive to the current information architecture and the fastest to ship, but it is the only concept of the three that still has _no day_ in it unless a stat tile literally says "2 days awaiting approval" and links out — it manages the symptom (forecasting is fine) without touching the root complaint ("I don't like it at all" is, per finding #1, partly "there is nothing here").

- **A. Restyle in place** — keep the current three sections, same order, same data; fix only the ceiling headline colour (#4), tick labels (#5), projection-note severity (#6), duplicate account block (#13), and the "Press N" hint on mobile (#15). Effort: S. Risk: low — it's CSS/markup only, no new query. Does not fix: #1, #2, #3, #7 — the page is still forecasting-only, still has no day, still hides WWA behind Alerts.
- **B. Restructure the page (Concept 3, money-and-risk cockpit)** — add a WWA count and pending-proposal count as top-line stat tiles with links out, fix the two duplicate ceiling cards into one differentiated widget (#3), fix chart defects (#8–#11). Effort: M — one new server query (`fetchWorkedWithoutApprovalRows`, already exists) plus a new stat-tile component, everything else is rearrangement of existing widgets. Risk: medium (touches the load function's shape, every consumer of `PageServerLoad` data). Unlocks: promises 2–4 are now genuinely servable; promise 1 (no WWA unnoticed) is servable but still one hop away (a link, not the fact itself inline).
- **C. Rethink the flow (Concept 1, attention queue)** — new home-screen IA: an ordered action list at the top (WWA days, pending proposals, overdue/soon-due invoices, active critical alerts), ceiling/forecast/concentration as a secondary "This period" strip beneath it. Effort: L — needs a new aggregation query across work units, proposals, invoices and alerts (each piece already queryable per finding #2 and the InvoicesAndMoney/AlertsStatesAndPWA areas; the aggregation itself is new), a new list component (can reuse `src/lib/layout/RecordList.svelte`'s existing row/card pattern rather than inventing one), and coordination with those two areas on exactly which fields the queue needs from each. Risk: medium-high — cross-area data contract, most implementation work, but it is the only option that makes promise 1 true _on the page itself_, not one click away.
- **Recommendation**: **C**, phased through **B** first. Ship B immediately (it is cheap, fixes the loudest visual complaints, and is a strict subset of C's data needs), then land the attention queue as the new top block once the WWA/proposal/invoice/alert feeds are agreed with the other areas — B's stat tiles become the queue's first three rows rather than being thrown away.

### Ceiling meter

- **A. Restyle in place** — bind `.figure` colour to `status.level` (amber/red past a threshold, matching `StatusIndicator`'s own palette so the two never disagree); replace the hover-only `title` on ticks with a permanent small numeric label under the track (e.g. "35%" under the threshold tick, "100%" under the limit tick) sized to fit without collision (only 2–3 ticks, unlike the 12-tick month axis); make `.projection-note` inherit `status.level`'s colour and weight once `projectedEnd` crosses a threshold. Effort: S. Risk: low, pure presentation. Does not fix: #3 (still two visually separate cards for one figure), #7 (still a different language from the concentration chart's reference line).
- **B. Restructure the widget** — one card per _basis_, not per ceiling: when two ceilings share `currentValue` (same `basis`), render one headline figure with two limit rows beneath it ("Soft ceiling: €85,000 — loses the regime next year" / "Hard ceiling: €100,000 — loses it immediately, VAT due"), each with its own status glyph and its own position on one shared track (two limit marks, one fill). This directly fixes #3 and #4 together — the shared number now visually _is_ one number, and each consequence gets its own severity marker rather than two identical green ticks. Effort: M — `CeilingView`/`ceiling.ts` needs a light grouping pass (group by `basis` before mapping to cards), CSS for the two-limit track. Risk: low-medium; must handle the general case where ceilings sharing a basis vary from 1 to N (a generic non-Italian pack may have zero or one).
- **C. Rethink the flow** — unify ceiling _and_ concentration-cap presentation into one shared "Limit" primitive (name for cross-cutting ask below) used both here and in `ConcentrationChart`'s reference line, so "a thing that must not be crossed" has exactly one visual grammar across the whole app, closing #7. Effort: L (new shared component, touches two chart modules, needs sign-off from whoever else in the design system consumes ceiling-shaped data). Risk: medium.
- **Recommendation**: **B**, with **A**'s fixes folded in as part of the same change (colour-binding the headline and labelling ticks is required work for the new two-limit card anyway). Reserve **C** for the design-system pass rather than this component alone — it's the right end state but shouldn't block landing B.

**At-a-glance target, concretely**: headline figure colour = status colour; a single sentence directly under it states the worst case in words ("On track — projected to stay under both thresholds" / "Projected to cross the hard ceiling by €X on [date]" / "Hard ceiling already crossed — VAT due since [date]"); the track keeps the dashed projection mark but the mark itself also gets a small numeric label, not just a hover title; when `crossed` is true the entire card gets a status-coloured left border (same "never colour alone, always a second cue" rule the sidebar's active state and `StatusIndicator` already use) so a crossed ceiling reads as urgent even in a quick scroll-past, not just on close inspection of the number.

### Cash calendar chart

Each defect from the brief, with a specific fix:

- **Axis label collision (#8)** — two changes, both cheap: (1) widen `barWidth + barGap` to use the page's actual available width instead of a fixed 44px pitch (the container is already up to 1152px on `wide`; at 12 bars that's ~85px/bar, enough for `formatMonthShort`'s output without collision) — `plotWidth`/`barWidth` become a function of container width, read via `bind:clientWidth` on `.plot-wrap`, degrading to horizontal scroll only below a real minimum bar width (~32px), not by default. (2) `Axis.svelte` gets an optional `skip` step (render every Nth label when ticks would collide, computed from `length / ticks.length` vs. an estimated label width) — a generic fix that also protects any future chart with a dense x-axis, not just this one.
- **Non-round y ticks (#9)** — replace `cashCalendarYTicks`'s `[0, top/2, top]` with a standard "nice number" step algorithm (round `yMax` up to the nearest 1/2/5×10ⁿ, e.g. d3-style `tickStep`), producing ticks like `0 / 3 000 / 6 000` instead of `0,00 / 3492,50 / 5985,00`. No new dependency — the algorithm is ~15 lines (find the power of ten, pick 1/2/5, round up); keep it in `cash-calendar.ts` next to the function it replaces, keep the "distinct ticks" guarantee from the existing `#143` regression comment.
- **Marker legend as paragraph (#10)** — add a `title`/programmatic label to each marker line carrying the _specific_ contract and date (already available as `markerLabel(marker)` — just wire it as an `aria-label`-equivalent visible affordance, e.g. a small on-hover/on-focus callout using the existing `Tooltip` component rather than only the generic dash-pattern key paragraph). On the phone list, stop concatenating every marker into one run-on sentence per month (`monthMarkers.map(markerLabel).join('; ')`) — render each as its own short `<li>` line ("Contratto quadro 2026 — finestra di irrevocabilità" ) so it wraps as a list item, not a paragraph, and cap at showing the nearest one with a "+N more" disclosure when a month has several.
- **Chart/table toggle (#12)** — lift `view` state one level, out of `ChartFrame` and into a single page-level preference (a `Grafico`/`Tabella` control in the dashboard's own "This period" header, or a persisted user setting) so picking "table" once applies to every chart on the page. `ChartFrame` keeps its own responsive default (table under 640px) as the fallback when no page-level preference has been set. Effort for this specific change: S.
- **Recommendation**: land the axis pitch/skip fix and the nice-number ticks together (same file, same PR, both are "the chart lies about its own scale" bugs) — **Effort M, Risk low** (pure computation change, `cash-calendar.test.ts` already exists to pin the new tick algorithm). Marker-label and toggle-lifting are independent follow-ups.

## Cross-cutting asks

- **A "Limit" / threshold-status primitive.** Both the ceiling meter and the concentration reference line are "a measured value against a cap, with a consequence." Name one shared component — headline figure (status-coloured), a track or bar with labelled limit/threshold marks (not hover-only), a plain-language worst-case sentence, and a status-coloured card border when crossed — states: `good` / `warning` (approaching) / `serious` / `critical` (crossed), each carrying `StatusIndicator`'s existing shape+glyph, never colour alone. Needed by: dashboard ceiling cards, concentration chart's reference line, and (per `AlertsStatesAndPWA`'s territory) any alert that names a ceiling.
- **A compact "stat tile."** A single number + label + optional trend/link, no chart chrome, for the "This period" strip (collected/committed/projected, days pending, WWA count). Needed by: this dashboard's stat strip, and likely the invoices/money area for "total outstanding," "days to next payment," etc.
- **An "attention row" / action-queue list item.** Status glyph + one-line description + link to the record, reusable across WWA days, pending proposals, overdue invoices and active alerts. `src/lib/layout/RecordList.svelte` already has the right row/card responsive pattern (table on desktop, card list on mobile via CSS, not JS) — extend it with a status-glyph-leading variant rather than inventing a new list component.
- **A page-level chart/table preference**, so `ChartFrame`'s per-instance toggle becomes an opt-out of a shared default rather than N independent controls on one page.
- **A "nice number" axis-tick helper** in the design system's chart utilities (currently ad hoc in `cash-calendar.ts`), so any future chart with a continuous y-axis gets round ticks for free instead of reinventing `[0, max/2, max]`.
- **Axis label collision handling** (skip-every-Nth or rotate) as a first-class `Axis.svelte` prop, not a per-chart workaround — the month axis here is the worst offender today but any dense categorical x-axis will hit the same wall.
