# Application shell, navigation & information architecture

## What is there now

**Sidebar** (`src/lib/nav/Sidebar.svelte`, data from `src/lib/nav/items.ts`). Fixed 240px column, `100svh`, visible ≥900px (`src/routes/+layout.svelte:67-71`). Renders `NAV_GROUPS`: three unlabeled `<ul>` blocks separated by hairlines — (Oggi, Calendario) / (Clienti, Fatture) / (Import, Comunicazioni, Avvisi[badge], Impostazioni) — no group headings, so the grouping logic is invisible to the user, only inferable from the gaps. Active state is a 3px left border + bold, never colour alone (`Sidebar.svelte:93-97`, a genuine accessibility strength — see screenshot `desktop-it/clients.png`). Below the groups, a `.foot` block glued to the bottom via `margin-top:auto` shows the signed-in email, `LanguageSwitch`, and a sign-out button, present in **every** screenshot (`desktop-it/*.png`, `dark-it/dashboard.png`). No icons anywhere, no search, no collapse control.

**BottomBar** (`src/lib/nav/BottomBar.svelte`), visible <900px (`+layout.svelte:67-75`). Fixed strip, four tabs hard-coded to `BOTTOM_BAR_HREFS = ['/', '/day/calendar', '/clients', '/invoices']` (`items.ts:47`) plus a 5th "Altro" (More) button that opens a native `<dialog>` sheet listing the remaining four nav items (Import, Comunicazioni, Avvisi, Impostazioni). Visible in every `mobile-it/*.png` shot, e.g. `mobile-it/day-calendar.png`, `mobile-it/proposals.png`. `.content{padding-bottom:72px}` on mobile (`+layout.svelte:58-63`) keeps page content clear of the fixed bar — confirmed: no screenshot shows text hidden under it.

**PageHeader** (`src/lib/nav/PageHeader.svelte`), rendered by `Page.svelte` on every screen. Two mutually-exclusive breadcrumb renderings controlled by CSS, both always in the DOM: an `<ol>` trail shown ≥640px, a single "Back to {parent}" link shown <640px (`PageHeader.svelte:35-40, 99-109`). Title is a plain `<h1>` built by string interpolation in each route's `load` (e.g. `m.clause_note_new_heading({ contract: contract.title })`), with optional `subtitle` and right-aligned `actions` snippet. Compare `desktop-it/contract-detail.png` (3-level trail: Clienti › Nordwind Logistics S.p.A. › Contratto quadro…) against `mobile-it/clause-note-new.png` (one line: "Torna a Contratto quadro 2026 — piattaforma logistica").

**Page width** (`src/lib/layout/Page.svelte:34-46`). `max-width: 48rem` (768px) by default, `72rem` (1152px) opt-in via `width="wide"`. Grep across `src/routes` shows exactly **three** of ~34 leaf routes use `wide`: `/` (dashboard), `/design`, `/invoices`. Everything else — `/clients` (`clients/+page.svelte:41`), `/day/calendar` (`day/calendar/+page.svelte:63`), `/clients/[id]` and `/clients/[id]/contracts/[contractId]` (both tables of `<dl>`/rows, no `width` prop) — renders at 768px on a 1440px screen. `desktop-it/clients.png` and `desktop-en/clients.png` show the client table ending at x≈810 with ~630px of blank page to its right.

**Shell composition** (`src/routes/+layout.svelte`). One conditional: `chrome = data.user !== null`. Chrome pages get Sidebar + content + BottomBar; `/sign-in` and `/offline` render bare. `+layout.server.ts` fetches `unreadAlerts` for the sidebar/bottom-bar badge on every authenticated request.

**Route tree** (`src/routes/**`, 37 leaf pages including `/sign-in` and `/offline`). Eight items live in `NAV_GROUPS` (`items.ts:19-40`): `/`, `/day/calendar`, `/clients`, `/invoices`, `/import`, `/mail`, `/alerts`, `/settings`. Two real product surfaces have **no nav entry at all**: `/proposals` (reachable only from a dashboard card, `+page.svelte:35`) and `/design` (reachable only by typing the URL — grep confirms zero `href`/`resolve('/design')` anywhere in `src/routes`, `xd://ast_edit`-free check via `grep`). `/design` nonetheless renders inside the full authenticated shell (`desktop-it/design.png` shows the identical sidebar as every other page) and is gated by the same `hooks.server.ts` session check as the ledger itself (`src/lib/server/route-guard.ts:7-36` does not list it as public) — it is not a security hole, but it is an unlabeled product surface hiding in the same address space as real client data.

## What is wrong

1. **BLOCKER — Proposals, the human-confirmation gate the product's core promise depends on, has no persistent navigation entry anywhere.** `NAV_GROUPS` (`items.ts:19-40`) omits `/proposals`; `BOTTOM_BAR_HREFS` and the derived "More" sheet (`BottomBar.svelte:8-10`) are both built from `NAV_GROUPS`, so `/proposals` is invisible on mobile too — not even behind "Altro". The only paths in are the dashboard's "Rivedi le proposte" card (which itself only shows while `pendingProposalsCount > 0`) and a typed URL. `mobile-it/proposals.png` confirms: none of the five bottom-bar tabs is marked active when you're on it — the shell doesn't know this page exists. For a ledger whose stated invariant is "agents propose, humans confirm" and whose promise is "no day worked without approval goes unnoticed," burying the confirmation queue behind a conditional homepage card is not a styling problem, it is a _findability_ failure with direct product-risk consequences: a proposal can sit unconfirmed indefinitely with no way to check on it except returning to the dashboard and hoping the badge is still there.

2. **BLOCKER — the sidebar's first, top-left nav item is labelled "Oggi"/"Today" but does not go to today.** `items.ts:22`: `{ href: '/', label: m.nav_today }`. `/` renders the dashboard: `<h1>mastro</h1>`, a marketing tagline (`m.landing_tagline`), two ceiling gauges and three charts (`desktop-it/dashboard.png`, `desktop-en/dashboard.png`). A user opening the app to check "did today get logged" — the single most frequent action this product exists for — lands on portfolio analytics instead. This is a navigation _label lying about its destination_, the most severe kind of IA defect: it actively misdirects rather than merely under-serving.

3. **MAJOR — "Fatture" (Invoices) in the sidebar silently means "unpaid invoices only."** Nav label: `m.nav_invoices` = "Fatture"/"Invoices" (`items.ts:29`). Destination heading: "Fatture non pagate"/"Unpaid invoices" (`desktop-it/invoices.png`, confirmed by report.json `h1`). A paid invoice — `2026/014`, visible only via direct link in `mobile-it/invoice-detail.png` ("Pagata il 28 ago 2026") — does not appear under the nav item that claims to be "Invoices." This is a _cannot-be-found_ defect, not merely an ugly one: there is no in-app path from the nav to a paid invoice at all.

4. **MAJOR — three unrelated top-level nav destinations (`Import`, `Comunicazioni`, and the nav-less `Proposte`) implement one workflow: turn an incoming document or mailbox into a confirmed ledger entry.** `desktop-it/import.png`, `desktop-it/mail.png` and `desktop-it/proposals.png` share no visual or navigational link to each other, despite `day-producer.ts`'s own architecture treating them as one pipeline (archived mail → agent proposal → human accept). The owner has to remember three section names for what is conceptually his inbox, and has to check three places (plus the dashboard card) to know if anything is waiting on him.

5. **MAJOR — the shell has no working "go to what's wrong" mechanic.** The sidebar's only global-attention signal is the `Avvisi` badge count (`Sidebar.svelte:34-38`, from `unreadAlerts` in `+layout.server.ts`). It funnels to a page whose cards name a day or invoice but carry no link to it (page-content issue, not mine to fix — but the _shell_ has nothing to add either: no notification centre, no toast, no highlighted destination). An owner who dismisses the badge by visiting `/alerts` has, from the shell's point of view, resolved the problem — there's no residual shell-level cue that the underlying invoice is still 34 days overdue.

6. **MAJOR — page width is capped at 768px for the pages that most need the extra 660–1150px a 1440px viewport offers, and the code's own escape hatch is applied almost at random.** `width="wide"` exists (`Page.svelte:19-23`) and is used on 3 routes: the dashboard (charts, arguably fine), `/design` (a reference page), and `/invoices` (a 6-column table, correctly wide). It is _not_ used on `/clients` (`clients/+page.svelte:41`, a 5-column table), `/day/calendar` (`day/calendar/+page.svelte:63`, a 7-column week grid), `/clients/[id]` or `/clients/[id]/contracts/[contractId]` (multi-`<dl>` detail pages with embedded tables — `desktop-it/contract-detail.png` shows five stacked sections all clipped to 768px). The pattern that should decide "wide" — "carries a table" — is exactly the lead's documented rule (`Page.svelte:19-21`) and is not followed by more than half the pages that meet it.

7. **MINOR — the desktop/mobile breadcrumb swap silently drops every intermediate level on phones, and the resulting back-label can be very long.** `PageHeader.svelte:35-40` documents the tradeoff explicitly and it's a reasonable one line-wrap-wise, but the consequence is real: on `desktop-it/contract-detail.png` a user can jump straight to "Clienti" or to "Nordwind Logistics S.p.A." from a clause-note-new page; on `mobile-it/clause-note-new.png` the only option is "Torna a Contratto quadro 2026 — piattaforma logistica" (51 characters, wraps to two lines, ~15% longer again once English strings translate to Italian). Getting back to the client list from three levels deep costs three taps on mobile, one on desktop.

8. **MINOR — `/design` is a dev/QA reference page indistinguishable, once reached, from a real product page.** It shares the exact authenticated shell (`desktop-it/design.png`) though it documents itself as "not a dashboard screen, and nothing on it is real data" (`design/+page.svelte:137`). Its own comment (`palette.css:5-6`) says "only the `/design` route renders them today" as a temporary state. Nothing marks it as internal; a bookmark, a shared link, or browser autocomplete could resurface it next to genuine client data with no visual distinction.

9. **MINOR — the sidebar's identity/session block (email · language · sign out) is duplicated in the dashboard's own page content, and nowhere else.** Confirmed by grep: the only other `sign-out` form in `src/routes` is `+page.svelte:84-86`; every other route relies solely on the sidebar. (`LanguageSwitch` also appears legitimately on `/settings` — that's correct IA, not duplication — and on `/sign-in`, which has no chrome at all.) The dashboard's extra footer (`+page.svelte:82-87`, visible in `desktop-it/dashboard.png` and `dark-it/dashboard.png`) serves no purpose the sidebar doesn't already serve one scroll away; it's dead weight specific to one page, not a systemic pattern — worth naming precisely so it isn't "fixed" everywhere at once when it only exists once.

10. **POLISH — no search, no jump-to, no command palette, despite the UI already teaching keyboard shortcuts.** `desktop-it/dashboard.png` shows "Premi N" under the primary CTA and `mobile-it/day-new.png` shows "Ctrl+Invio (⌘+Invio su Mac) salva da qualsiasi campo del modulo" — on a phone, where neither shortcut can ever be used. There is no shortcuts panel or palette that lists what exists, and no way to jump directly to a client, invoice number, or date without walking Sidebar → list → row every time. Low severity today (3 seeded clients), but the IA has no growth path built in.

11. **POLISH — no period switcher shared across dashboard, calendar and invoices.** The cash-calendar chart has no period control at all (full history baked in), `/day/calendar` has its own prev/today/next, `/invoices` has none (it isn't time-scoped). Three different — or absent — ways to answer "what period am I looking at," never shared.

## Options

### Sidebar (`Sidebar.svelte`, `items.ts`)

- **A. Restyle in place** — add group headings (small caps label above each `<ul>`) so the three invisible clusters read as clusters; add an icon slot per item (16–20px, from the shared component set) for faster scanning once destinations exceed ~6. Effort S. Risk: low. Does not fix mislabeling, missing destinations, or the ingestion fragmentation.
- **B. Restructure the groups** — re-derive `NAV_GROUPS` around the corrected IA below (Daily / Ledger / Inbox / System), add `/proposals` as a first-class item with its own badge (pending count, same pattern as `Avvisi`), move `/design` out of `NAV_GROUPS`'s address space entirely (see Route map). Effort M. Risk: low, `items.ts` is already a single data module both nav surfaces read from, so the change is one file plus new message keys. Unlocks the top-level reduction below.
- **C. Rethink the shell** — collapsible sidebar with a persistent icon rail + expandable labels (like a normal SaaS app), sticky search field at the top. Effort L. Risk: medium — needs a collapse-state design and touch/keyboard parity; probably premature for a single-user app with 8–11 destinations.
- **Recommendation**: **B**. The data-model separation the code already has makes this a same-day change, and it directly fixes findings 1, 2 and 4 (proposals promoted, "Today" relabelled/rescoped, ingestion merged) without inventing new interaction patterns.

### BottomBar + "More" sheet (`BottomBar.svelte`)

- **A. Restyle in place** — add icons to the four fixed tabs and to the sheet rows (thumb-scanning without reading five words). Effort S. Risk: low. Does not fix reachability of `/proposals`.
- **B. Restructure the tab set** — keep 4 fixed tabs but swap the set to match the corrected IA (Today / Calendar / Clients / **Inbox** replacing Invoices, since money-in-limbo is one tap from Today's card and Inbox is the higher-frequency action); put Invoices, Alerts, Settings in "More". Effort S–M (data-only change, same component). Risk: low.
- **C. Replace "More" with a real sheet component** — the native `<dialog>` today is unstyled beyond a border and has no icons, no grouping, no visual weight difference from a plain list; rebuild it as the shared design system's bottom-sheet primitive (see Cross-cutting asks) so it matches whatever styling language ships elsewhere. Effort M. Risk: low.
- **Recommendation**: **B**, and fold **C**'s component request into the design-system ask. B is the one change on this screen that actually restores reachability (finding 1) instead of only re-skinning an already-functional pattern.

### PageHeader — breadcrumbs, back-link, titles (`PageHeader.svelte`, `crumbs.ts`)

- **A. Restyle in place** — shorten the mobile back-label to the _nearest_ parent's short name only (already what happens; the length problem is the parent's _own_ title being long, e.g. contract titles), or truncate with a `title=` tooltip. Effort S. Risk: low — a truncated back-link on a day-ledger the owner navigates one-handed is a real usability cost if the truncation hides which contract it's returning to.
- **B. Restructure the header for long titles** — cap `h1` to two lines with a `title` attribute holding the full string (works today, CSS-only), and stop _concatenating_ generated titles ("Nuova nota sulla clausola per {contract.title}") in favour of a two-line pattern: small eyebrow label ("Nuova nota sulla clausola") over the record name, styled distinctly instead of one run-on sentence. Effort S–M (touches every `m.*_heading({...})` call site, but they're all single-line template edits). Risk: low, i18n-safe since it only changes composition, not the message keys' words.
- **C. Rethink navigation entirely for edit/create flows** — nested resources (clause note, expense, rate card) open as a slide-over/sheet anchored to the contract page instead of a full route+breadcrumb, so there is nothing to concatenate: the parent page is still visible behind the sheet. Effort L. Risk: medium — changes routing contracts other pages (ClientsAndContracts) already depend on; needs to be a joint decision, not a shell-only change.
- **Recommendation**: **B**. It fixes the readability problem (finding 7 and the lead's #10) without touching routes other agents own, and is a small, mechanical, low-risk change across ~14 `*_heading()` call sites.

### Page width container (`Page.svelte`)

- **A. Restyle in place** — apply the existing `width="wide"` prop to every route that already fails the code's own rule: `/clients`, `/day/calendar`, `/clients/[id]`, `/clients/[id]/contracts/[contractId]`. Effort S (four one-line prop additions). Risk: none — the prop and CSS already exist and are exercised elsewhere. Does not fix the deeper issue that "text" vs "wide" is a binary guess made per-page by whoever wrote it, with no rule enforced anywhere.
- **B. Restructure the sizing model** — replace the two named buckets with a rule the layout enforces itself: any page whose direct child is a table/grid component (shared `DataTable`/`RecordList`) renders wide automatically; forms and record detail stay text-width. Effort M. Risk: low — mechanical, and it removes an entire class of future "someone forgot `width=\"wide\"`" bugs.
- **C. Rethink the constraint entirely** — drop the fixed rem caps for a fluid `clamp()` (e.g. `clamp(20rem, 90vw, 96rem)`) so the content column tracks the viewport instead of jumping between two fixed stops; combine with a persistent side rail so wide pages use the freed width for a detail/preview pane rather than just wider tables. Effort L. Risk: medium — needs real content to look right at ultrawide, and interacts with the design system's spacing scale (not mine to set).
- **Recommendation**: **A now, B next.** A is a zero-risk same-day fix for the four worst offenders (finding 6); B is what stops it from regressing the next time someone adds a table page and forgets the prop.

### Route map / information architecture

- **A. Relabel and rescope in place, keep every URL** — rename "Oggi" to something that matches its content (or make `/` genuinely a "today" surface — see route map below), rescope `/invoices` to show all invoices with an "unpaid" default filter/tab, add `/proposals` to `NAV_GROUPS`. Effort M. Risk: low — no URL changes, so no redirects/bookmarks to manage.
- **B. Merge the ingestion trio into one destination** — `/import`, `/mail` (+ its `contracts/[id]`, `register`, `templates/*` children) and `/proposals` become tabs of one route, e.g. `/inbox?tab=import|mail|proposals`, one nav item, one badge (sum of pending imports + unread mail + pending proposals). Effort M–L: mostly a routing/IA change, each existing page's content moves under a shared tab shell, `mailCrumbs()`/`proposalsCrumbs()` collapse into one crumb builder. Risk: medium — three other agents' pages move address; needs the merge coordinated, not done unilaterally.
- **C. Also fold day surfaces and rethink the home route** — `/day/date/[date]` (today a full navigation + list of links, `day/date/[date]/+page.svelte:16-24`) becomes a small popover/sheet triggered from the calendar cell instead of a route, since it has no purpose beyond disambiguating a multi-entry date; `/` becomes the actual "today" surface (today's state + the two primary CTAs), and the current dashboard content moves to a new `/overview` reachable from a renamed nav item. Effort L. Risk: medium-high — `/` is also very likely the OAuth post-sign-in landing target and default redirect; needs a redirect-target check before moving content off it.
- **Recommendation**: **A first** (same-day, fixes the two BLOCKERs with no coordination cost), **B next** (the one change that reduces top-level nav destinations, see table below), **C only after DashboardAndCeilings agrees on where dashboard content should live** — it's the only option here that reaches into another agent's territory.

### Global affordances that don't exist

- **A. Add the missing pieces as isolated components** — a `⌘K`/`Ctrl K` command palette (jump to any client/contract/invoice/day by typing; list every keyboard shortcut, replacing the bare "Premi N" hint text); a notification/attention icon in the sidebar header (bell + count, opens a small popover of the same alerts data, each row a real link — closing the loop finding 5 leaves for the shell) rather than only the "Avvisi" nav row; a period switcher component (month/quarter/year) shared by dashboard, calendar and invoices via a single `?period=` query convention. - **B. Ship the minimum viable set now** — palette deferred (real cost, marginal payoff at 3 clients / dozens of days); ship only the notification popover (closes finding 5 without waiting on AlertsStatesAndPWA's page redesign) and the period-switcher convention (used immediately by the invoices rescope above). Effort S–M. Risk: low.
- **Recommendation**: **B**. The palette is real future work but not urgent at current data volume; the notification popover and period switcher pay for themselves immediately and are pure-shell changes no other agent's page needs to change first.

## Cross-cutting asks

- **Nav icon set** — 16–20px monochrome icons for: Today, Calendar, Clients, Invoices, Inbox (or Import/Mail/Proposals if not merged), Alerts, Settings, plus a generic "back"/chevron glyph for the breadcrumb collapse. Needed by Sidebar and BottomBar simultaneously; must exist as one shared icon component so both surfaces stay in sync the way `items.ts` already keeps their data in sync.
- **Badge component** — currently a bespoke `<span class="badge">` in `Sidebar.svelte:98-105` and an unstyled `<span>` in `BottomBar.svelte:39-41`; needs to become one shared "count badge" primitive (states: zero/hidden, 1–99, 99+) used by Alerts today and by the proposed Inbox/notification-popover badges tomorrow.
- **Bottom-sheet primitive** — for the "More" nav sheet today, and for the `/day/date/[date]` disambiguation-as-sheet option (Route map, Option C). States: open/closed, list vs. custom content, safe-area-aware bottom padding (BottomBar already does this correctly for the tab bar — `env(safe-area-inset-bottom)`, `BottomBar.svelte:57` — the sheet should reuse the same value).
- **Command-palette / search primitive** — if Option A above is picked later: an overlay input + result-list component, fuzzy match, keyboard nav (arrows + enter), used by the shell only but likely to be reused by any future "jump to" affordance inside a page.
- **Table/grid width rule** — ask DesignSystem to fold "wide" vs "text" into a token/rule (Page-width Option B above) rather than a per-page boolean the shell alone can't enforce.
- **Focus ring + hover/active states for nav items** — `Sidebar.svelte` and `BottomBar.svelte` currently define `active` only (border + weight); neither defines a visible `:hover` or `:focus-visible` state, which the design system's control audit should confirm before this doc's fixes ship (keyboard-only navigation, e.g. tabbing to a sidebar item, currently outputs the browser default outline only, unverified against dark theme).
